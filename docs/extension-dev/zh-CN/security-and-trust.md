# 安全与信任

> 扩展的权限边界、编辑器的保护机制、以及作为扩展作者的责任。这一页的规则没有例外条款，发布前请逐条对照。

## 权限边界：扩展不是沙箱

第三方扩展会以**接近编辑器本身的权限**运行——它们能访问用户的文件和网络。编辑器**不会**把扩展关进沙箱，**安装即意味着相当程度的信任**。

这不是措辞保守，是架构事实：所有扩展运行在同一个扩展宿主进程里，可以 `require('node:fs')`、可以 spawn 子进程。`workspace.fs` API 的路径策略只约束走 API 的扩展，不构成安全边界。webview 界面运行在受限的内嵌页面里（只能加载扩展目录与显式声明位置的资源、受 CSP 约束），但**这不是等同于浏览器网页的强沙箱**——承载它的扩展进程本身仍拥有接近编辑器的权限。

作为作者，请如实对待这一点：

- **不要**在你的 README、市场描述或任何物料里宣称扩展被「沙箱隔离」。
- 把「用户安装我的扩展 = 把相当的信任交给我」当作设计前提，最小化你需要的权限和数据。

## 编辑器的两层保护（以及它们不是什么）

编辑器做了两层保护，但它们只是提醒、不能替用户判断：

- **发布者信任提示**：用户首次安装某个发布者的扩展时会看到确认提示；确认后同一发布者的后续扩展不再重复询问。——这意味着你的 publisher 身份本身就是信任资产，请保护好发布 token（见 [发布扩展](./publishing.md)）。
- **恶意扩展拦截**：市场会标记已知的恶意扩展，编辑器拒绝安装；已装的扩展事后被标记，会在下次启动时自动禁用并通知用户。——这是事后救济，不是事前审核。

## Workspace Trust 与你的扩展

用户可以把工作区标记为「不受信任」，此时默认不激活需要信任的扩展。你用 `capabilities.untrustedWorkspaces` 声明扩展在不受信任工作区里的行为：

- 有 `main` 的扩展**未声明时默认 `false`**——即不受信任的工作区里不激活。这是最安全的默认值，请只在确有理由时改它。
- 纯 UI 扩展（没有 `main`，比如纯主题）默认 `true`。
- 声明 `supported: 'limited'` 时，扩展在不受信任工作区里激活，但宿主会限制你声明的 `restrictedConfigurations` 之外的配置写入；你必须在 `description` 里写清楚哪些功能在受限模式下不可用。

声明示例与字段语义见 [扩展的结构](./extension-anatomy.md#capabilitiesuntrustedworkspaces)。判断标准很简单：**你的扩展会按工作区内容执行代码、跑构建、发网络请求吗？** 会，就不要声明支持不受信任的工作区。

## 作者责任清单

- **token 即身份**：泄露的发布 token 等于把该 publisher 名下所有扩展交给攻击者。token 只放 `~/.uex/config.json` 或 CI secret，绝不提交进仓库。
- **依赖即代码**：你的运行时依赖会以你的扩展的身份执行。钉版本、审依赖、别引入你不认识的传递依赖。
- **数据最小化**：能本地处理的不上传；必须上传的在 README 写清楚传什么、传到哪。
- **诚实声明**：`untrustedWorkspaces`、`description`、市场元数据里写的能力与实际行为一致。
