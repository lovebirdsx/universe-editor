# Agent 触发器（Triggers）

触发器让 Agent **在没有人盯着的时候**按条件自动开工：到点跑一次、轮询一个命令、或者每当 Swarm 出现待你处理的审核时启动一个会话，让它完成分析并把结论写成结构化结果。适合「定时汇总」「持续分诊」「轮到我就提醒」这类重复劳动。

> 触发器**默认全部关闭**。它需要你手写一份配置（JSON，带注释也可以），并且每个触发器都要显式写 `"enabled": true` 才会自动运行。一次自动化运行仍然是一个**普通 Agent 会话**——会出现在 Sessions 列表里，可以点开逐条查看它做了什么。

## 它是怎么工作的

一次运行（run）大致经历：

1. **触发源产生事件**。四种来源分别是手动、定时、命令轮询和 Swarm 审核。
2. **去重**。每个事件有一个稳定的 key（例如 Swarm 审核用 `swarm:<reviewId>`）。同一个 key 只会运行一次，编辑器重启后也不会重复。
3. **排队**。全局与每个触发器都有并发上限；超出时按 `overflow` 排队或丢弃。
4. **找一个窗口**。触发器必须声明一个本机工作区文件夹。编辑器会复用已打开该文件夹的窗口；没有就**在后台开一个隐藏窗口**（后台常驻模式下），再把运行交给它。
5. **创建自动化会话**。Agent 以你配置的 skill / prompt / 模式运行，并受一套**比手动会话更严格**的权限策略约束。
6. **产出结果**。Agent 把结论写进本次运行的目录；会话结束后编辑器读取判决，只有 `auto-approve` 才执行白名单内的动作。
7. **收尾**。更新 Sessions 列表里的徽标与摘要、发通知、写审计；失败会退避，连续失败会自动暂停。

触发器由**主进程**统一调度，不是每个窗口各跑一份。因此关掉某个窗口不会让同一个触发器在别的窗口重复触发。

## 第 1 步：打开配置文件

打开命令面板（`Ctrl+Shift+P`），执行 **触发器: 打开配置**。

- 文件不存在时会先创建一个**带注释的示例文件**再打开；已经存在时**绝不覆盖**。
- 文件位置：本机用户数据目录下的 `<userData>/triggers/triggers.json`（打包版在 Windows 上通常是 `%APPDATA%\Universe Editor\triggers\triggers.json`；开发版或自定义 `--user-data-dir` 时以「打开配置」实际打开的文件为准）。
- 保存后**热加载**，不需要重启编辑器。文件是 JSONC，可以写 `//` 注释和尾随逗号；编辑器会为已知字段提供补全与校验提示。
- 示例里的 `workspace` 是占位路径 `X:/workspace`，**必须改成你自己的本机文件夹**。

整份文件写坏时：

- 编辑器**启动时**读到非法文件 → 使用空配置（所有触发器都不运行），并在日志里告警。
- 运行期间外部编辑写坏 → **保留上一份有效配置**继续运行，同时告警。

单个触发器配置有误只影响它自己：它会以「配置无效」出现在列表里并显示错误，不会运行；其它触发器照常。

## 配置结构

```jsonc
{
  "version": 1,
  "maxConcurrentRuns": 2,
  "triggers": [
    {
      "id": "swarm-triage",
      "name": "Swarm 分诊",
      "enabled": false,
      "workspace": "X:/workspace",
      "source": { "type": "swarm-review" },
      "session": {
        "agent": "claude-code",
        "skill": "swarm-triage",
        "prompt": "处理 Swarm 审核 #{{event.reviewId}}（作者 {{event.author}}）",
        "mcpServers": ["swarm"],
        "budget": { "maxCostUsd": 1, "timeoutMin": 30, "approvalTimeoutMin": 1440 }
      },
      "allowedActions": ["swarm.vote", "swarm.comment"],
      "concurrency": 1,
      "overflow": "queue"
    }
  ]
}
```

## 字段说明

### 顶层字段

| 字段 | 必填 | 类型 / 取值 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `version` | 否 | `1` | `1` | 配置版本，目前只能是 1；写别的值会让整份文件失效。 |
| `maxConcurrentRuns` | 否 | 1–10 的整数 | `2` | 全局同时运行的自动化会话上限。 |
| `triggers` | 是 | 数组 | 空 | 触发器列表。 |

### 单个触发器

| 字段 | 必填 | 类型 / 取值 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | 是 | `^[a-z0-9][a-z0-9-]{0,63}$` | — | 唯一 id，小写字母、数字、连字符；重复会让相关条目都标为无效。 |
| `name` | 否 | 非空字符串 | 同 `id` | 列表与通知里显示的名字。 |
| `enabled` | 否 | 布尔 | `false` | **只有显式为 `true` 才会自动运行**。手动「立即运行」不受它限制。 |
| `workspace` | 是 | 本机绝对文件夹路径 | — | 例如 `X:/workspace`。必须是本地文件夹；不支持 `\\server\share`、`//server/share`、`file://` 等 URI 或远程 authority。 |
| `source` | 是 | 对象 | — | 触发源，见下一节。 |
| `session` | 是 | 对象 | — | 会话配置；至少要能给出 `skill` 或非空 `prompt`。 |
| `allowedActions` | 否 | 字符串数组 | `[]` | 允许自动执行的动作白名单，取值只能是 `swarm.vote` / `swarm.comment` / `swarm.approve`。 |
| `concurrency` | 否 | 1–10 的整数 | `1` | 该触发器自己的并发上限。 |
| `overflow` | 否 | `queue` / `drop` | `queue` | 并发已满时：`queue` 排队（每个触发器队列上限 20），`drop` 直接丢弃新事件。 |

### `session` 字段

| 字段 | 必填 | 类型 / 取值 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `agent` | 否 | 非空字符串 | 编辑器默认 Agent | 例如 `claude-code`、`codex`。不是内置已知的 Agent（没有保守默认档）时，必须同时显式配置 `mode`，否则该轮启动失败。 |
| `cwd` | 否 | 相对路径 | 工作区根目录 | 相对 `workspace`，必须落在其下；禁止以 `/`、盘符开头、包含 `..` 或 `:`，也不能有被 Windows 静默改写的尾随 `.` / 空格。 |
| `mode` | 否 | 非空字符串 | 该 Agent 的保守档（Claude Code 为 `default`，Codex 为 `read-only`） | 显式的 mode id。`bypassPermissions` / `auto` / `acceptEdits` / `agent` / `full-access` / `agent-full-access` / `danger-full-access`（不区分大小写）属于高权限模式，**必须先执行「触发器: 确认高权限模式…」**。 |
| `model` | 否 | 非空字符串 | 该 Agent 的默认模型 | 本次会话使用的模型 id。 |
| `skill` | 否 | `^[A-Za-z0-9][A-Za-z0-9:_-]*$` | 无 | 技能名。渲染 prompt 时会自动作为首行 `/技能名` 显式调用。 |
| `prompt` | 否* | 字符串 | 空 | 提示词模板；可用 `{{event.字段}}` 引用事件数据。 |
| `mcpServers` | 否 | 非空字符串数组 | 不限制 | 创建会话时**固定（pin）**使用的 MCP 服务器名，之后不会跟随设置变化。 |
| `budget` | 否 | 对象 | 见下 | 单次运行预算。 |

\* `skill` 与 `prompt` 至少要有一个；两者都没有（或 `session` 整体缺失）时该触发器无效。

`budget` 三个字段都是**正数**，写 `0` 或负数同样会被判为配置无效：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `maxCostUsd` | `1` | 单次运行的费用上限（美元）。达到或超过后取消该轮。 |
| `timeoutMin` | `30` | 会话**活跃时间**上限（分钟）。等待审批卡 / 提问卡的时间不计入。 |
| `approvalTimeoutMin` | `1440`（24 小时） | 单张审批卡 / 提问卡的最长等待时间（分钟）。超时取消该轮，结果记为 `approval-timeout`。 |

## 四种触发源

`source.type` 四选一。

### `manual`：手动运行

```jsonc
{ "id": "adhoc", "workspace": "X:/workspace",
  "source": { "type": "manual" },
  "session": { "prompt": "整理今天的待办" } }
```

只有命令 **触发器: 立即运行触发器…**（或列表里的「立即运行」）会产生事件。`enabled` 不需要为 `true`；但「已暂停」「全部暂停」「高权限模式待确认」仍然会阻止运行——暂停时 `runNow` 会直接以「该触发器已暂停」拒绝。手动运行不受失败退避和启动后的调度宽限期限制。

### `schedule`：定时运行

```jsonc
{ "type": "schedule", "cron": "0 9 * * 1", "onMissed": "skip" }
```

或使用固定间隔：

```jsonc
{ "type": "schedule", "everyMin": 60, "onMissed": "skip" }
```

| 字段 | 说明 |
| --- | --- |
| `cron` | 标准 **5 字段** cron：`分 时 日 月 周`。与 `everyMin` **必须且只能设置一个**。 |
| `everyMin` | 整数分钟（≥ 1），固定间隔。 |
| `onMissed` | 编辑器关闭期间错过的触发如何处理：`skip`（默认）丢弃；`catch-up-once` 在下次启动后补跑**最近一次**。 |

cron 的写法：

- 字段范围：分 `0-59`、时 `0-23`、日 `1-31`、月 `1-12`、周 `0-7`（`0` 与 `7` 都表示周日）。
- 支持 `*`、逗号枚举 `1,15`、范围 `1-5`、步长 `*/10` 或 `1-30/5`。
- **不支持** `MON`、`JAN` 这类英文名，也不支持 `?`、`@daily` 等扩展语法。
- 使用**本机本地时区**，不是 UTC。
- 日与周同时受限时，按标准 cron 的语义取**或**（任一匹配即触发）。
- 不可能发生的组合（例如 `0 0 31 2 *`）会记一条「没有下一次触发」的警告，不会运行。

其它行为：

- **刚启用时不会补跑**：`lastScheduledAt` 为空时只安排下一次，不追历史。
- 计划时刻过后 **2 分钟内**仍算「按时到达」；更早的才算错过，由 `onMissed` 决定。
- 启动后有一个约 **60 秒的调度宽限期**（等窗口恢复和设置同步稳定），宽限期结束才开始调度。

### `poll`：命令轮询

```jsonc
{
  "type": "poll",
  "intervalSec": 600,
  "fetch": { "type": "command", "command": "node scripts/fetch-reqs.js", "timeoutSec": 60 },
  "keyField": "id"
}
```

| 字段 | 说明 |
| --- | --- |
| `intervalSec` | 轮询间隔（秒），整数且 **≥ 30**。 |
| `fetch.type` | 目前只支持 `"command"`。 |
| `fetch.command` | 要执行的命令行（经 shell 执行），工作目录是触发器的 `workspace`。 |
| `fetch.timeoutSec` | 命令超时（秒），整数 `1–600`，默认 `60`。 |
| `keyField` | 每条数据里用作去重键的字段名，例如 `id`。 |

命令输出要求：

- stdout 必须是**合法 JSON**，并且是以下两种形态之一：
  - 一个数组：`[{ "id": 1, "title": "..." }, ...]`
  - 一个带 `items` 数组的对象：`{ "items": [ ... ] }`
- 输出上限 **1 MB**，超过会被停止并记为失败。
- 数组里每个元素必须是对象，且 `keyField` 的值是**非空字符串或数字**；否则该条被跳过。`keyField` 相同的条目只触发一次。
- 除 `keyField` 外的其它字段会进入事件数据：字符串 / 数字 / 布尔原样保留；对象和数组会转成 JSON 字符串，最长 4000 字符；`null` 会被丢弃。

基线（baseline）语义：

- 触发器**第一次成功取数**只「建基线」：把当前所有条目记为已见，**不触发任何运行**，避免一启用就被历史数据淹没。
- 之后的轮询只对**新出现的 key** 触发。
- 修改 `keyField` / `fetch.command` / `intervalSec`（或更换 `source.type`）会**清空该源的基线标记与已见 key**，下一次成功取数重新建基线，不会把新条目误当成已见。

失败处理：

- 命令超时、退出码非 0、输出非法 JSON / 形状不对、超过 1 MB，都会记为一次失败。
- 超时或输出超限时会**结束整棵子进程树**（Windows 用 `taskkill /T`，POSIX 杀进程组），不会留下后台孙进程继续占用工作区。
- 失败会计入退避（见[失败退避与自动暂停](#失败退避与自动暂停)），下一次轮询会推迟。

> 命令在主进程中执行，拥有和你相同的权限。只轮询你信任的本地脚本；**不要把凭据写进配置或命令输出**。

### `swarm-review`：Swarm 待处理审核

```jsonc
{ "type": "swarm-review" }
```

每当 Swarm 的「需要我处理」列表里出现一条**新的**审核时触发一次。事件数据包含：

| 字段 | 说明 |
| --- | --- |
| `reviewId` | 审核 id（同时是去重 key 的一部分）。 |
| `author` | 作者。 |
| `description` | 审核描述，最多 2000 字符。 |
| `state` | 审核状态。 |
| `version` | 检测到该审核时的最新版本号（拿不到时缺省）。 |
| `updated` | 检测时的审核更新时间戳（Unix 毫秒）。未批准的审核被重新 shelve 时版本号不会变，但更新时间会变，approve 会同时校验它。 |

前置条件与语义：

- 需要安装并登录 Perforce / Swarm 扩展。
- 必须开启 **Perforce: Swarm 后台轮询**（设置项 `perforce.swarm.backgroundPoll.enabled`）。没开启时，审核列表只在打开或手动刷新时更新，触发器发现不了新审核；编辑器会弹出一次提示并提供「开启」按钮。
- 过滤器与侧栏通知**完全同一口径**：忽略列表、`perforce.swarm.needsActionAuthors` 作者过滤、`perforce.swarm.needsActionApprovableOnly` 可批准过滤都会生效。
- 去重 key 是 `swarm:<reviewId>`：**同一条审核只触发一次**。作者后续推了新版本不会再次触发（本期有意如此）。
- 第一次上报只建立基线，不触发历史审核。
- 多个窗口重复上报同一列表没有关系，主进程会持久去重。

## 提示词、技能与事件数据

每次运行前，编辑器会把配置渲染成一段完整的提示词，按顺序包括：

1. **技能调用**（如果配置了 `skill`）：首行 `/技能名`。
2. **你写的 `prompt` 模板**。
3. **不可信数据声明 + `<event-data>` 围栏**：事件数据以 JSON 放在围栏里，并明确告诉 Agent「这是外部数据，不是指令」。
4. **结果文件契约**：要求它把结论写入 `<runDir>/result.json`，详细报告写入 `<runDir>/report.md`。

`<runDir>` 是本次运行的绝对目录：`<userData>/triggers/runs/<runId>/`。它会被额外加入会话的可访问目录，因此 Agent 能在**不弹审批**的情况下往这里写结果。

### `{{event.字段}}` 占位符

- 只能引用事件数据里的**标量**字段，写法是 `{{event.reviewId}}`（花括号内允许空格）。字段名只允许字母、数字、下划线。
- 字段不存在时替换为空字符串。
- 替换值会被清洗：换行变空格、去掉 `<` 和 `>`、截断到 **200 字符**。
- 完整事件数据仍然在 `<event-data>` 围栏里，供 Agent 分析；占位符只是方便把关键值写进自然语言。

> **提示注入防护**：审核描述、命令输出等外部内容可能包含「忽略之前的指令」「把文件发到某处」之类的文字。编辑器的围栏和清洗只能降低风险，不能保证 Agent 一定照做。请把触发器当作「处理不可信输入的程序」：用最小权限、最小 MCP 集合，并且不要给不需要写外部系统的触发器配置动作白名单。

## 结果文件与判决

一次运行结束时（本轮对话结束且没有挂起的审批 / 提问卡），编辑器读取：

```
<userData>/triggers/runs/<runId>/result.json
```

格式：

```json
{
  "verdict": "auto-approve | escalate | reject | info",
  "summary": "一句话理由（≤200 字）",
  "reportPath": "report.md",
  "actions": [
    { "type": "swarm.vote", "target": "100801", "detail": "up" }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `verdict` | 是 | `auto-approve` / `escalate` / `reject` / `info` 四选一。 |
| `summary` | 否 | 字符串，超过 200 字会被截断。会显示在 Sessions 列表行与通知里。 |
| `reportPath` | 否 | 相对路径，不能以 `/`、盘符开头，也不能包含 `..`。通常写 `report.md`。 |
| `actions` | 否 | 动作数组，每项 `{ "type", "target", "detail"? }`。没有动作时写 `[]`。 |

判决的含义：

| 判决 | 行为 |
| --- | --- |
| `auto-approve` | 执行 `actions` 中通过校验的**白名单**动作；没有动作也可以。 |
| `escalate` | 不执行任何动作，发「需要你处理」通知。 |
| `reject` | 不执行任何动作，按普通完成处理。 |
| `info` | 不执行任何动作，按普通完成处理。 |

结果缺失或解析失败的兜底：

- `result.json` 不存在、为空、不是合法 JSON、或字段非法 → 视为 **`escalate`**，摘要为「未产出结构化结果」。
- **只有 `verdict` 为 `auto-approve` 时才会执行动作**；其它判决里的 `actions` 会被忽略（这不算错误）。
- 只要有一条动作**校验不通过**（不在白名单、目标不匹配、参数非法、未确认 approve，或非 `swarm-review` 源却要求 Swarm 动作），整份判决降级为 `escalate`，**一个动作都不执行**。
- 校验通过后如果某条动作**执行失败**，排在它后面的动作**立即停止**，整份判决同样降级为 `escalate`；此前已经执行成功的动作无法撤回，摘要会列出「已执行：…（不可回滚）」。`swarm.approve` 的 TOCTOU 守卫是例外：它在任何动作执行前统一预检，不通过时一个动作都不会执行。

动作默认由编辑器执行，不需要给 Agent 配置 Swarm 写工具；Agent 只负责产出判决。

## 自动动作

首期支持三种动作，全部走 Perforce 扩展已有的 Swarm 命令：

| 动作 | `detail` | 目标与守卫 |
| --- | --- | --- |
| `swarm.vote` | 必须是 `up` 或 `down` | `target` 是审核 id。投票会带上事件里的版本号（如果有）。 |
| `swarm.comment` | 评论正文，非空且 ≤ 4000 字 | 实际发出的正文会自动加前缀 `[由触发器 <名称> 自动生成] `，方便评审者区分。 |
| `swarm.approve` | 无 | 见下。 |

`swarm.approve` 的额外约束：

1. 触发器必须在 `allowedActions` 里**明确列入** `swarm.approve`。
2. 必须由你执行 **触发器: 确认自动 approve…** 做二次确认。确认绑定当前触发器配置的指纹——**改任何配置都会让确认失效**，需要重新确认。
3. 事件里必须同时带审核版本号与更新时间戳；缺一个都直接拒绝（无法确认审核没变）。
4. 执行前会**重新拉取审核**，要求：仍然可以 approve（存在 approved 转换）、**最新版本号与事件里的版本一致**、且**更新时间戳也与事件里的一致**。任一不满足就降级为 `escalate`。这是为了防止「Agent 分析完之后作者又推了新改动」（未批准的审核重新 shelve 时版本号不变，只能靠更新时间识别）。
5. 这个预检在**执行任何动作之前**统一完成：只要 approve 守卫不通过，整批动作（包括排在前面的投票 / 评论）都不会执行。校验通过后，动作按 `actions` 的顺序执行。
6. 永远以 `commit: false` 执行——**自动 approve 绝不提交**。

目标约束：

- 对 `swarm-review` 源，动作的 `target` 必须等于本次事件的 `reviewId`，否则整份判决降级。
- 只有 `swarm-review` 源可以执行 `swarm.*` 动作。`manual` / `schedule` / `poll` 源的 `auto-approve` 判决里只要出现 Swarm 动作，整批动作都会被拒绝并降级为 `escalate`（这些源没有「事件对应审核」的目标）。非 Swarm 动作仍只受白名单约束。

## 自动化会话的权限策略

自动化会话在**无人值守**下运行，所以编辑器会**覆盖你的个人自动放行设置**：

| 机制 | 手动会话 | 自动化会话 |
| --- | --- | --- |
| 个人自动批准（`acp.permissions.autoApprove` / 按工具类型的自动放行） | 生效 | **不应用** |
| 计划权限策略（`agentSettings.claude.planPermissionPolicy`） | 生效 | 强制 **Manual** |
| 计划审批卡倒计时（`acp.plan.autoExecute`） | 生效 | **禁用**，一律等人工 |
| 「始终允许」选项 | 提供 | **隐藏**，也不会写回你的个人规则 |
| 写入本次运行目录（`runDir`）的文件 | 正常审批 | 满足条件时**自动允许一次** |

「写入运行目录自动允许」的条件是：工具调用类型为**编辑（写文件）**，请求明确列出了目标路径、所有路径都在 `runDir` 下，且路径里不含 `..`。读文件、执行命令、删除 / 移动文件等其它请求仍然会走审批卡。这个自动放行不解析符号链接；但创建符号链接本身需要执行命令，而命令仍要人工审批，因此无人值守时 Agent 无法先伪造一个再借它越界。

其余权限请求照常弹出审批卡，并走现有的桌面通知 / 手机收件箱 / 推送。没人处理时，等待到 `approvalTimeoutMin` 就取消该轮，运行结果记为 `approval-timeout`。

### 高权限模式（bypass 类）

`mode` 配成 `bypassPermissions` / `auto` / `acceptEdits` / `agent` / `full-access` / `agent-full-access` / `danger-full-access`（不区分大小写）时：

- 触发器状态下会显示 **⚠**，并进入「等待确认」。
- **未确认时该触发器完全不运行**（定时、轮询、Swarm、手动「立即运行」都会被阻止），不是降级到保守模式。
- 执行 **触发器: 确认高权限模式…** 并阅读警告后才会放行。确认绑定当前配置指纹；改任何配置都需要重新确认。
- 高权限模式下 Agent 可以不询问就执行任意操作，而触发器又是无人值守的——**除非你完全清楚风险，否则不要开启**。

## 预算与超时

每次运行独立计预算：

- **费用**：会话累计费用达到 `maxCostUsd` 就取消该轮，结果记为 `budget-exceeded`。预算以美元计价；拿不到费用数据、或 Agent 上报的币种不是 USD 时，这条限制不生效（Triggers 日志会告警一次），时间类限制仍然生效。
- **活跃时间**：`timeoutMin` 只累计会话**真正活跃**的时间；停在审批卡 / 提问卡上的时间会被扣除。超时后取消该轮，结果记为 `timeout`。
- **审批等待**：每张审批卡 / 提问卡单独计时，超过 `approvalTimeoutMin` 取消该轮，结果记为 `approval-timeout`。
- 断线自动恢复 / 重连仍在**同一轮 run** 内，消耗同一份预算。

也就是说：`timeoutMin` 管「Agent 实际工作了多久」，`approvalTimeoutMin` 管「你多久没理它」。

此外，主进程还给每轮运行设了一个兜底看门狗（`timeoutMin + approvalTimeoutMin + 10 分钟`宽限）：如果窗口异常、一直不上报结束状态，到期会按失败处理并尝试取消该轮。这样卡死的窗口不会永久占住并发槽位。

## 并发与排队

- 全局上限 `maxConcurrentRuns`（默认 2）与每个触发器的 `concurrency`（默认 1）同时生效。
- 一个并发槽位从**会话创建**一直占到**运行结束**，包括等待审批的时间。
- 并发已满且 `overflow` 为 `queue` 时：事件排队，每个触发器最多 20 条；队列满时**丢弃最旧的一条**并记日志（新事件仍会入队）。
- `overflow` 为 `drop` 时：并发已满就直接丢弃新事件。
- 排队中的事件会写入磁盘；编辑器重启后，**尚未开始**的排队事件会重新入队，**已经开始的**不会重放。
- 排队事件被丢弃或启动失败时，它的去重 key 会被移除，之后同一 key 再次出现时可以重新触发。

## 失败退避与自动暂停

以下情况记为失败：轮询命令失败、没有可用窗口 / 开窗失败 / 等窗口超时、窗口在 120 秒内没有接受运行、工作区未受信任、会话创建失败、运行本身以失败结束、运行中的窗口被关闭或重新加载、运行超时未上报结束（看门狗）。

- 连续失败按 **1 分钟、2 分钟、4 分钟……** 指数退避，上限 **1 小时**。
- **退避对所有来源生效**：`schedule` 在退避期内到点的槽位直接跳过（不补跑），退避结束后从下一个槽位继续；`poll` 推迟到退避结束再取数；`swarm-review` 在退避期内上报的审核不消费，退避结束后的下一次上报仍会正常触发。
- **手动「立即运行」不受退避限制**（用户显式操作优先）；启动后的调度宽限期只约束 `schedule` / `poll` 的定时（以及重启后待重放事件的入队），手动运行随时可以执行。
- **连续失败 5 次**会自动暂停该触发器，写审计并弹一条系统通知。通知里会提示用「触发器: 列出触发器」恢复。
- 手动暂停 / 恢复：恢复会清零连续失败次数与退避。**暂停会丢弃该触发器已经排队的运行**（不中断正在运行的会话），释放它们的去重 key，恢复后同一事件可以再次触发。
- 重启时尚未开始的排队事件会保留；如果当时触发器处于暂停 / 待确认状态，这些待重放事件会一直保留到恢复或确认后再入队。已开始的事件绝不重放。
- 「触发器: 全部暂停」会丢弃所有排队事件（不会中断正在运行的会话），待重放事件同样保留到「全部恢复」；「全部恢复」重新开始调度。

## 在 Sessions 列表里找到自动化会话

每次运行都会创建一个**持久化**的普通会话（标题形如 `触发器名 · 事件key`），所以在辅助侧边栏的 Sessions 列表里能找到它：

- 行内有一个 **⚡** 徽标，悬停显示「由触发器 触发器名 启动 · eventKey」。
- 有判决时，标题下方会显示判决标签（自动通过 / 需要人工处理 / 已拒绝 / 信息）与摘要。
- 列表的漏斗菜单里有**来源过滤**：全部会话 / 手动创建 / 触发器。
- 点开就是正常聊天：可以看它读了什么、改了什么、为什么这样判断；也可以继续追问或恢复会话。

历史上限：

- 会话历史总共最多保留 100 条。
- **非置顶的自动化会话最多只占 30 个名额**；超出时优先淘汰最旧的自动化会话，把名额留给手动会话。
- 置顶的自动化会话不受这 30 条限制；如果置顶数量本身超过总上限，仍按置顶的最近使用顺序淘汰。

## 通知与手机收件箱

- 运行结束会在**发起运行的窗口**弹一条通知：
  - 正常完成：信息级「已完成：触发器名」。
  - 判决为 `escalate`：警告级「需要你处理：触发器名 · 摘要」。
  - 费用超限 / 超时 / 审批超时 / 失败：警告级「触发器运行未完成：触发器名（原因）」。
  - 被取消（例如你在会话里主动停止该轮）：不弹。
  - 通知上都有「打开会话」按钮。
- 自动暂停会用系统通知（主进程弹出，没有窗口也能看到）。
- 手机侧：自动化会话照常出现在收件箱，带 **⚡ 触发器名** 与判决摘要；它的**审批 / 提问事件总是推送到手机**，即使 PC 窗口正聚焦。点击提醒可直接进入会话。配置手机见[手机遥控](./mobile.md)。

## 日志、状态与审计

都位于 `<userData>/triggers/`：

| 位置 | 内容 |
| --- | --- |
| 输出面板 → **Triggers** 通道 | 调度门控、事件 key、运行开始 / 结束、失败与退避、轮询失败、确认操作等。**只记触发器 id、事件 key、runId、sessionId 等标识，不记事件数据、提示词、判决摘要或命令输出。** |
| `triggers.json` | 你的配置（热加载）。 |
| `state.json` | 机器写入的运行状态：去重 key、暂停标记、失败计数与退避、上次调度时间、基线标记、高权限 / approve 的确认指纹。不要手改。 |
| `audit.jsonl` | 审计：运行开始 / 结束（含执行了哪些动作及结果）、**每条动作单独一行**（含拒绝 / 失败原因）、暂停 / 恢复、全部暂停 / 恢复、两次确认、自动暂停。 |
| `runs/<runId>/` | 每次运行的结果目录：`result.json`、`report.md`。默认只保留最近 **200** 个运行目录；仍在运行 / 排队中的目录不会被清理。 |
| `pending/<runId>.json` | 排队事件的临时负载，运行开始后会删除。 |

排查顺序：先看 **Triggers** 日志通道，再看 `audit.jsonl`，最后看对应 `runs/<runId>/` 里的结果与报告。

## 安全与隐私

- **提示注入是首要风险**。事件数据来自外部系统（审核描述、命令输出等），可能包含恶意指令。编辑器会做围栏、清洗和长度截断，但不能保证模型完全免疫。请按「处理不可信输入」来设计：不要给不需要的 MCP，不要让触发器拥有写生产系统的能力。
- **数据会发给模型供应商**。提示词模板、事件数据（可能包含作者、描述、简历等个人信息）都会进入会话并发送给当前 Agent 配置的模型供应商。`result.json` / `report.md` 只留在本机运行目录。涉及简历、个人信息或机密内容时，先确认供应商与合规要求。
- **推荐最小 MCP 集合**。只 pin 真正需要的 MCP；默认不要加联网、邮件、IM、工单写入之类的 MCP，除非触发器确实需要且你已评估过注入风险。
- **不要在配置里写凭据**。`triggers.json` 是明文本地文件；命令输出、事件数据也会进入提示词。密钥请放在环境变量或你信任的本地凭据存储中，由轮询脚本自行读取。凭据也不要放进事件数据。
- **动作是真实操作**。`swarm.vote` / `swarm.comment` 会以你的身份产生公开记录；`swarm.approve` 还额外需要二次确认，且永不 commit。请在 `allowedActions` 里只放你愿意让机器自动做的事。
- **高权限模式**只在确认后生效，确认与配置指纹绑定；改配置就会失效。不要为了省事长期开启。
- **工作区必须受信任**。自动化运行会拒绝在未受信任的工作区启动；远程工作区不支持触发器。
- 手机拥有与 PC 相同的操控权限，请只在自己的设备上配对并设置锁屏（见[手机遥控](./mobile.md)）。

## 与看门狗、空闲回收和历史上限的交互

- **卡死看门狗**不豁免自动化会话。它会排除等待审批的时间；长时间无输出的工具调用被判卡死后会热重连，对本次运行透明。
- **空闲回收**只发生在回合结束之后，对正在运行的 run 没有影响。被回收的自动化会话再次打开时仍保持受限权限策略，但 `runDir` 路径范围不会跨重启保留（只保留非路径类限制）。
- **历史上限**：自动化会话最多保留 30 条非置顶记录，不挤占手动会话；置顶不受限。
- **退出确认**：运行中的自动化会话照常计入「有运行中会话」，退出时可能被中断并给出提示。

```jsonc
      "session": {
        "skill": "team-weekly-digest",
        "prompt": "汇总上周的提交与 Swarm 审核，输出一份内部摘要。",
        "budget": { "maxCostUsd": 1, "timeoutMin": 30, "approvalTimeoutMin": 1440 }
      },
      "allowedActions": []
    }
  ]
}
```

> 如果要让 `swarm-triage` 自动 approve，除了把 `swarm.approve` 加进 `allowedActions`，还必须执行 **触发器: 确认自动 approve…**；否则任何 approve 动作都会让整份判决降级为 `escalate`。

## 常见问题

**启用了，为什么一直不运行？**

依次检查：

1. `enabled` 是否为 `true`；是否被单个暂停或「全部暂停」。
2. 是否处于「等待确认」（配置了 bypass 类 mode 但没确认）。
3. 配置是否「无效」——在「触发器: 列出触发器」里看错误。
4. 启动后是否还没过约 60 秒的调度宽限期。
5. `schedule`：刚启用不会补跑历史，要等下一次；cron 是否写错或不可能发生。
6. `poll`：第一次成功取数只建基线；命令是否失败或输出格式不对。
7. `swarm-review`：Swarm 后台轮询是否开启；审核是否真的出现在「需要我处理」里（作者 / 可批准过滤会生效）。
8. 工作区是否是本机文件夹、是否已受信任。
9. 并发是否已满、是否在退避中（手动「立即运行」不受退避限制）。

**暂停后还能「立即运行」吗？**

不能。暂停会优先于手动运行，直接拒绝并提示该触发器已暂停；先执行 **触发器: 恢复触发器…**（或「全部恢复」），并且高权限模式需要确认时先确认，之后才能运行。

**为什么判决是 `auto-approve`，动作却没执行？**

- 动作类型不在 `allowedActions`；或对 Swarm 源来说 `target` 不是本次审核 id。
- 触发器不是 `swarm-review` 源（`manual` / `schedule` / `poll`）：这些源不能执行任何 `swarm.*` 动作。
- `swarm.vote` 的 `detail` 不是 `up` / `down`；`swarm.comment` 正文为空或超 4000 字。
- `swarm.approve` 没有二次确认、事件缺版本号或更新时间、重新拉取失败、当前已不可 approve、版本或更新时间已变化。
- 只要有一条不满足，整份判决会降级为 `escalate`，可以在摘要与审计里看到原因。

**为什么没有任何结果文件？**

Agent 可能没有按契约写入 `result.json`（例如技能没加载、提前结束、预算 / 超时先终止）。这时判决会兜底为 `escalate`，摘要「未产出结构化结果」。去 `runs/<runId>/` 看有没有半成品，或在会话里追问 Agent。

**自动化会话一直卡在审批？**

它不会应用你的个人自动放行设置，除了写 `runDir` 的请求外都需要人工处理。处理审批卡，或调大 `approvalTimeoutMin`；无人值守场景请把预算和审批超时设为合理值。

**会不会自动提交代码？**

不会。首期动作只有 Swarm 投票、评论、approve；approve 永远 `commit: false`。Agent 本身仍可改本机文件（受权限策略约束），但这些改动不会自动提交。

**运行太贵 / 太久怎么办？**

调小 `budget.maxCostUsd` 与 `timeoutMin`；在 `session.model` 指定更便宜的模型；把任务拆成更小的 skill；检查事件数据是否过大（尤其轮询命令一次吐出大量字段）。

**能配工作区级触发器吗？**

本期只读用户级 `triggers.json`，不支持工作区级定义。配置随本机用户数据目录走，不会同步到其它电脑。

**支持远程工作区吗？**

不支持。`workspace` 必须是本机绝对文件夹；远程 authority 无法通过校验。

**配置改坏了会怎样？**

运行期间改坏会保留上一份有效配置；启动时读坏会退回空配置。看 **触发器: 查看日志** 或 Triggers 日志通道里的告警。
