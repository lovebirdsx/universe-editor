## 冲突解决（resolve）

当仓库里有了比你 have 版本更新的改动，[拉取](./sync-and-status.md)或[取出搁置](./changelists-and-shelving.md#取出搁置unshelve)时可能需要 **resolve**。待解决的文件会聚到一个置顶的 **需要合并** 组里（没有需要合并的文件时不显示）。

三种解决方式，都在该组文件行的行内按钮 / 右键菜单上：

- **解决冲突**（自动合并，`p4 resolve -am`）：让 Perforce 尝试自动合并。能自动合并的文件被直接解决；有真正冲突的文件保持待解决状态。**完成后有明确反馈**——比如「已自动合并 2 个，1 个仍需手动解决」，并带 **解决冲突** 按钮直接打开剩余文件的三向合并编辑器；全部已解决（本次没有实际合并发生时）提示「解决冲突完成」。
- **接受我的版本**（`p4 resolve -ay`）：丢弃对方的改动、保留你的。会先确认（提示「对方的改动将被丢弃」）。
- **接受对方的版本**（`p4 resolve -at`）：丢弃你的本地改动、采纳对方的。会先确认（提示「你的本地改动将被丢弃」）。

对整个 changelist 一键解决：在该组组头上选 **解决 Changelist 冲突**（自动合并该组全部待解决文件）。

### 三向合并编辑器

对仍有真正冲突的文件，选 **在合并编辑器中解决** 打开三向合并编辑器：左侧**基准** = 你的 have 版本（`#have`），右侧**传入** = 服务器 head 版本（`#head`），结果窗格预填磁盘上的文件（含 p4 冲突标记）。在结果里手动合并后**保存即接受**——保存会把合并结果作为「我的版本」解决掉该文件。

和 Git 冲突一样，打开含这些标记的文件时，每处冲突上方会浮现一行操作按钮：**采用当前更改**（保留 YOURS，即你的工作区版本）、**采用传入更改**（采纳 THEIRS，即仓库版本）、**保留双方更改**、**比较更改**（并排对比两侧）。点选后标记自动清除。

## Blame：这行是谁改的

Perforce 文件同样支持行内 **Blame（溯源）**，与 Git 共用同一界面：底层用 `p4 annotate` 得到每行归属的 changelist，再取该 changelist 的描述与作者。

- 打开 Blame 的方式、行内提示的显示偏好，都沿用 [Git 的 Blame 说明](../git/blame-and-history.md)。
- 显示相关的 `scm.blame.*` 偏好设置对 Perforce 文件同样生效——它们控制的是**界面呈现**，与后端是 Git 还是 Perforce 无关。

## 设置一览

在[设置](../customization/settings.md)里搜索 `perforce`：

| 设置项 | 作用 | 默认 |
|---|---|---|
| `perforce.port` | 兜底 `P4PORT`（`server:port`） | 空 |
| `perforce.user` | 兜底 `P4USER` | 空 |
| `perforce.client` | 兜底 `P4CLIENT` | 空 |
| `perforce.autoEdit` | 编辑未签出文件时自动 `p4 edit` | 关 |
| `perforce.reconcileHint.enabled` | 在资源管理器中标记磁盘上改过但未签出的文件（改动徽标 M/A/D，其父文件夹随之变色），见[收集改动](./daily-workflow.md#收集改动reconcile)。只检查当前显示在屏幕上的行，开销随可见行数而非 depot 规模增长；作用范围由[工作区范围](#关于工作区范围)决定 | 开 |
| `perforce.reconcileScan.maxBatchDurationMs` | 后台预热扫描单个目录批次的时间上限（毫秒，默认 10000），超时批次自动拆分子目录 | 10000 |
| `perforce.reconcile.excludeFolders` | 收集类界面忽略的文件夹：后台收集扫描、资源管理器改动徽标、窄查，以及收集 / 清理里未签出的那一半。支持相对 / 绝对路径，嵌套的排除条目自动折叠。**只是收集降噪，不是范围来源**：普通拉取、已签出文件与既有 changelist 不受影响；明确选中被它覆盖的路径做收集 / 清理时会先弹确认，确认只对本次所选生效。详见[收集降噪](#收集降噪) | `[]` |
| `perforce.p4delta.enabled` | 找到 p4delta 可执行文件即启用（**不再有版本门槛**）：后台收集扫描、逐文件改动核对、普通拉取与强制拉取（见[拉取由谁执行](./sync-and-status.md#拉取由谁执行)；按修订号 / 按日期的形态仍走原生），以及收集改动 / 收集到指定 Changelist / 清理文件（`p4 clean`）这三个写操作；关闭则始终用 p4 原生命令（工作区范围不受影响——它由编辑器自己解析） | 开 |
| `perforce.p4delta.path` | p4delta 可执行文件路径；留空则从 `PATH` 查找（远程开发时填远端机器上的路径） | 空 |
| `perforce.p4delta.autoInstall` | 在找不到现成 p4delta 的机器上，自动下载并维护一份（见[关于 p4delta 引擎](#关于-p4delta-引擎编辑器自装副本)）。只要别处能找到一份就完全不碰它、也不联网；关掉表示改为手动安装 | 开 |
| `perforce.p4delta.downloadBaseUrl` | 从自定义镜像而非 GitHub Releases 下载 p4delta 的基址（连不上公网的机器用）。需提供 `latest.json` / `SHA256SUMS` / 对应 zip；留空用官方发布。作用域为 machine，工作区设置无法改写下载源 | 空 |
| `perforce.refreshInterval` | 轮询刷新间隔（秒，最小 10，`0` 关闭） | 关 |
| `perforce.openedByOthers.autoCheck` | 后台「他人占用」扫描 + 灰字 | 开 |
| `perforce.openedByOthers.intervalSec` | 两次「他人占用」扫描的最小间隔秒数（最小 30） | 300 |
| `perforce.commandTimeout` | 单个 p4 进程最长存活秒数，超时强杀（`0` 不限制）。约束「永久挂死」而非「执行慢」——卡死在冻结网络盘上的 p4 不会再无限期占住并发槽。**不约束内容传输命令**（sync/submit/shelve/unshelve/revert/clean，它们随字节数增长且可取消） | 600 |
| `perforce.syncParallelThreads` | `p4 sync` 并行拉取线程数（`--parallel=threads=N`，`0` 串行）。需服务器开 `net.parallel.max`，不支持时 p4 静默回落串行。只对**由 p4 执行**的拉取生效 | 4 |
| `perforce.cache.enabled` | 缓存 p4 结果以减少服务器往返 | 开 |
| `perforce.cache.workspaceTtl` | 工作区状态缓存有效期（毫秒，`0` 关闭工作区缓存） | 4000 |
| `perforce.cache.diskLimitMb` | 不可变历史数据磁盘缓存上限（MB，`0` 关闭落盘） | 50 |

连接类设置只作兜底，推荐优先用 `p4 set` / P4CONFIG，见[概览与连接](./overview.md#连接是怎么建立的)。

### 关于工作区范围

工作区范围（daily scope）来自 **client 根目录下的 `.p4delta-scope` 范围文件**（固定就是这一个位置，不再沿上级目录链查找），由编辑器与 p4delta 引擎各自读取**同一份文件**。文件是 JSON（名字不带 `.json` 后缀，编辑器按文件名识别为 JSON 并高亮）：

```json
{
  "include": [{ "dir": "." }],
  "exclude": [{ "dir": "Generated" }, { "file": "local.txt" }]
}
```

- 每条条目恰好写一个 **`dir`**（含整棵子树）或 **`file`**（精确匹配这一个文件），类型由写出来的键决定——**不按本地存不存在去猜**，「本地还不存在的输出目录」正是一条常见的 `dir`。
- 路径是 **client 根目录相对**的 `/` 拼法；反斜杠是错误，`..` 越出根目录一律报错。
- **省略 `include`**（或整份写成 `{}`）= 整个 client 根目录；**`include: []`** = 明确的空集，与"没写"不是一回事。**`exclude` 永远优先于包含。**
- 文件损坏（非法 JSON、未知字段、类型不对、路径非法）一律**报错**，绝不退化成"没有配置"——一条被静默丢掉的排除项会让范围**放大**。

实际范围 = **打开的文件夹 ∩ 配置文件里的包含项**，再排除掉命中的排除项。省略 `include` 的配置文件，其包含项就是**整个 client 根目录**（与打开的文件夹取交集后仍是打开的文件夹）——"只排除几个目录"不必把其余目录逐个列出来。范围文件自己会被排除在范围之外：它出现在工作区里不会被当成一处改动。

范围作用于：后台收集扫描（改动发现、资源管理器改动徽标）、收集改动、收集到指定 Changelist、清理文件（`p4 clean`），以及[拉取](./sync-and-status.md#拉取由谁执行)（拉取最新版本 / 按 changelist 档——普通拉取与强制拉取一样按它裁剪）。

- **工作区里没有范围文件**时行为与从前一致：打开的文件夹就是范围。
- **有范围文件但读不了、或内容非法**：范围未知，日常操作（发现、收集、清理）一律拒绝，并提示「工作区范围无法解析，日常 Perforce 操作（发现、收集、清理）已暂停：{原因}」。范围未知时按工作区范围执行的**无参拉取**（普通或强制）同样会被拒绝（提示以「未执行拉取：…」开头），不会悄悄退化成"按整个工作区来"。**范围解析不需要 p4delta**——文件由编辑器自己读，p4delta 只负责它擅长的那几个操作。
- 编辑、新建或删除范围文件后**即时重解析并重新扫描**：资源管理器改动徽标与收集范围随新范围立即生效，无需重载窗口。一次操作按**执行那一刻**的文件解析，所以预览与随后的执行之间改了文件，执行用的是新内容——[预览将要拉取的内容](./sync-and-status.md#预览将要拉取的内容)之后改了范围时，拉取会提示「工作区范围在预览之后发生了变化——本次按当前配置执行」（只是告诉你旧清单不作数，不会拒绝或延迟），重新预览一次即可看到新范围的清单。
- **确认框到执行之间改了配置，也是按当前配置执行**：破坏性操作（清理未收集的改动等）的确认框会点明「本次按当前配置执行：要丢弃的清单在执行时按当时生效的工作区范围与收集排除规则重新确定。」——你确认的就是这件事本身，编辑器既不拿一份过期的清单去执行，也不因为你改了配置就拒绝；重新执行 / 重新预览即可看到新规则下的清单。

**你明确指定的路径若不被范围完整覆盖，不会被静默裁剪。** 只要选中 / 右键的路径里有一个落在范围外或命中排除，编辑器就先弹选择框（标题里写明「…包含工作区范围未完整覆盖的路径：…。这些路径由你明确指定，因此不会被静默裁剪——请选择如何处理。」），两个按钮：

- **遵守工作区范围**：丢掉未覆盖的路径；若丢完什么都不剩，则不执行该操作并提示「所选路径在工作区范围之外，或被排除规则隐藏。」；
- **按所选执行**：仅这一次运行**不带范围文件**（等价于"按你选的来"）。这个豁免只属于那一次运行，不会影响后续任何操作。其余情况一律不静默放宽。

范围**不影响已签出文件的 `p4 revert`**——已签出文件在 SCM 面板里本就可见、是显式收集过的，还原照常作用。

#### 收集降噪

它和范围文件是**两层不同的东西**。范围文件回答「哪些路径属于我的工作」（会影响拉取与一切日常操作）；这个设置只让**收集类界面**别再看见某些文件夹——后台收集扫描、资源管理器改动徽标、窄查，以及收集 / 清理里未签出的那一半（已签出的文件在 SCM 面板里本就可见，不受影响）。它**不是范围来源**：既不放宽也不收窄工作区范围，普通拉取、`p4 opened` 与既有 changelist 的语义完整保留。

生成目录（`gen`、`build` 之类）适合写进这里：它们只是一遍遍被扫描出来的噪声，不是「不该被拉取的内容」。反过来，要真正**禁止**某些路径被拉取 / 收集，那才是范围文件里 `exclude`（`{"dir": "路径"}` 或 `{"file": "路径"}`）的职责。

- 值支持相对（相对工作区根）或绝对路径；嵌套在别的排除目录下的条目会自动折叠。
- 明确选中被它覆盖的文件夹（或其下路径）做收集或清理时**不静默**：编辑器先弹确认，列出这些路径，两个按钮——**跳过它们**（默认，什么都不做，并提示「所选路径在工作区范围之外，或被排除规则隐藏。」）或**按所选执行**（仅这一次为所选目标解除规则）。确认只对本次所选生效，同一批里的祖先目录仍会被裁剪绕开。

### 关于 p4delta 引擎（编辑器自装副本）

p4delta 是可选的加速引擎（取代后台收集扫描、逐文件改动核对、普通与强制拉取，以及收集 / 清理这几个写操作；找不到时静默回退原生 p4）。编辑器按下面的顺序找它，**前四级任意一级命中就完全不联网**：

1. 环境变量 `UNIVERSE_P4DELTA_PATH`（逃生舱与自动化测试）
2. 设置里的 `perforce.p4delta.path`
3. `PATH`
4. `%LOCALAPPDATA%\Programs\p4delta\p4delta.exe`（p4delta 自带的安装位置）
5. **编辑器自己下载维护的那一份**（存放在本扩展的存储目录，仅 Windows x64）

第 5 级就是自动安装：默认开启，激活后在后台查一次上游最新版本，需要时静默下载、校验摘要、安装并**热生效**——装好即用于后续操作，无需重启。装成或升级成时弹一次通知（带**显示日志**按钮）；已在最新、跳过、失败这些情况只写 **Perforce 输出**日志，不打扰你。

命令面板里的 **Perforce: 安装或更新 p4delta** 是同一件事的手动版本：跳过「最近刚检查过」的节流和 `perforce.p4delta.autoInstall` 开关（关掉它正是为了改用这条命令），并且**即使这台机器上已经有自装副本也照装**。唯一拦得住它的是 `perforce.p4delta.enabled`：引擎整个停用时，下载没有意义。

两点是有意为之的：

- **自装副本优先**：只要第 1–4 级能找到一份，编辑器就完全不碰它——这也意味着**那份自装副本不会被自动升级**（要升级就跑上面的命令，或更新你自己的安装）。
- **没有版本门槛**：找到就用（只检查文件存在），不存在「版本太低所以不用」这一档。

连不上公网的机器可以自建镜像：把 `perforce.p4delta.downloadBaseUrl` 指向一个纯静态目录，里面放三个文件——`latest.json`（内容是 `{"version":"0.1.10"}`）、`SHA256SUMS`（p4delta 官方发布里的同名文件，可原样放）、以及 `p4delta-0.1.10-x86_64-pc-windows-msvc.zip`（官方发布的对应资产）。镜像下**摘要校验同样是强制的**：清单缺失、没列出该资产、或摘要对不上，一律拒绝安装，绝不会执行未经校验的二进制。

自动安装只对 **Windows x64** 生效（上游目前只发布这一种构建）；其他平台会跳过并在日志里说明，请自行安装。

### 关于缓存

因为每次 p4 操作都要往返服务器，集成会缓存结果以提速：

- **不可变历史数据**（已提交变更的详情、某个具体版本的文件内容）永不改变，会被缓存并**跨会话落盘**——重开 [Perforce Graph](./perforce-graph.md) 或查看历史 diff 无需再次请求服务器。
- **工作区状态**（已打开文件、路径映射等）可能变化，只做短时（`workspaceTtl`）缓存，且**任何变更操作后立即失效**，因此界面里的操作总能看到最新结果。`workspaceTtl` 只影响「编辑器之外」（例如命令行 `p4`、他人）改动后被察觉的延迟；把它设为 `0` 可关闭工作区缓存（不可变历史缓存仍生效）。

## 密钥安全

密码 / ticket **绝不写入明文设置文件，也不经任何网络协议明文传输**。登录凭据交给 `p4` 自身按 `P4TICKETS` 机制保存，集成不自行保管。这与本编辑器对所有敏感凭据的一致红线相同。

## 排错

- **面板不出现**：确认 `p4` 在 `PATH` 中，且该文件夹在某个 Perforce 客户端根目录下（`p4 info` 能报出 client root）。
- **提示未登录 / 会话过期**：用面板 ⋯ 菜单的**登录**重新登录。
- **看不到最新服务器状态**：手动**刷新**，或开启 `perforce.refreshInterval` 轮询。
- **收集 / 清理被拒绝，提示范围问题**：工作区里放着范围文件，但它读不了或内容非法（范围无法解析）。按提示处理，见[关于工作区范围](#关于工作区范围)。
- **改了文件但面板里没有**：普通改动会出现在面板的 **改动**（Changes）组；若该组隐藏、资源管理器也没有改动徽标，说明文件已签出且没有未收集改动，或已被[收集改动](./daily-workflow.md#收集改动reconcile)。想把它收进某个 changelist，在资源管理器右键 **收集改动** 即可。
- **想看底层命令**：在面板标题栏 ⋯ 菜单选 **显示输出**，打开 **Perforce 输出**底栏看完整日志。

更多通用问题见[常见问题](../reference/faq.md)与[疑难排查](../reference/troubleshooting.md)。
