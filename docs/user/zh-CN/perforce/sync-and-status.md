## 三种拉取方式

Perforce 的「拿版本」对应 `p4 sync`。编辑器提供三个命令，覆盖 P4V 里最常用的三条路径：

| 命令 | 什么时候用 | 入口 |
|---|---|---|
| **拉取最新版本** | 最常用：把最新（`#head`）拿下来，无确认、直接执行 | Explorer 右键（一级菜单）、命令面板 |
| **拉取版本…** | 需要指定版本：按 changelist / 日期 / 修订号，或强制覆盖 | Explorer 右键 **Perforce ▸** 子菜单、命令面板 |
| **预览将要拉取的内容** | 拉之前先看会动哪些文件；只读，绝不改动任何东西 | Explorer 右键 **Perforce ▸** 子菜单、命令面板 |

> 状态栏的「可更新」计数不再等价于「拉取最新版本」：点击它先问你要同步到哪个变更列表（最新版本仍是第一项、一键可达），见[状态感知](#状态感知)。

## 拉取最新版本

入口：

- Explorer 右键一级菜单的 **拉取最新版本**（文件与目录都可用；对目录右键 = 递归拉取整个子目录）；
- 状态栏的修订指示器（如 `#68 / ↓#69`）——点击它只拉取**当前这个文件**；
- 命令面板搜 "Perforce: 拉取最新版本"。

上面三个入口都无需确认、直接执行。状态栏的「可更新」计数**不是**这条命令的入口：点击它先弹出「要同步到哪个变更列表」，选定后再按[作用域](#拉取的作用域)拉取整个作用域（最新版本仍是第一项、一键可达，见[状态感知](#状态感知)）。

完成后弹结果：**已更新 N 个文件**；有文件正被签出、p4 不会覆盖它们时，附「· M 个已跳过（正在签出中）」；有文件拉完需要合并时，附「· K 个需要合并」并提供 **解决冲突** 按钮，直接进入[冲突解决](./resolve-and-advanced.md#冲突解决resolve)流程。全部已是最新时提示 **已是最新版本**。

### 有文件被跳过：本地改了但没签出

如果文件在本地被改过却没签出，Perforce **不会**用服务器版本覆盖它——你的改动优先。此时拉取会跳过这些文件并提示 **N 个文件未更新——它们有尚未收集的本地修改**，附三个按钮：

- **收集改动**：把这些本地改动收集（签出）进 changelist。收集之后再拉一次，Perforce 就会把服务器的新版本与你的改动排进[合并](./resolve-and-advanced.md#冲突解决resolve)，两边都不丢。这是推荐路径。
- **查看差异**：先看清本地到底改了什么再决定（多个文件时先让你选一个）。
- **强制拉取**：直接用服务器版本覆盖本地文件。**未收集的改动会永久丢失、不可撤销**，所以点它之后还有一次确认；只在确定本地改动是废弃的时候用。

> 注意跳过与失败的区别：被跳过的文件不影响同一次拉取里的其它文件，它们照常更新——提示条会把两件事一起报（如「1 个文件未更新…… · 已更新 9 个文件」），不会因为有跳过就瞒下已经拿到的。

## 拉取指定版本

入口在 Explorer 右键 **Perforce ▸ 拉取版本…** 或命令面板 "Perforce: 拉取版本…"，弹出五档选择（对齐 P4V 的 Get Revision）：

| 选项 | 含义 | 后续 |
|---|---|---|
| 最新版本 | 与「拉取最新版本」相同（`#head`） | 直接执行 |
| 指定 changelist 时的版本… | 拉取到某个 changelist 为止的状态（`@12345`） | 输入 changelist 编号 |
| 指定日期时的版本… | 拉取到某一天的状态（`@2026/08/01`） | 输入日期 `yyyy/mm/dd`，可带时间 |
| 指定修订号… | 拉取某个具体修订（`#4`） | 输入修订号 |
| 强制拉取最新版本（覆盖本地文件） | `#head -f`：覆盖本地文件，即使 Perforce 认为它们已是最新 | 二次确认 |

输入框支持直接带前缀 `@` / `#`（如 `@12345`、`#4`），不会重复加前缀。

> **强制拉取会先确认**：它会覆盖本地文件，其中**未收集的改动将丢失，且不可撤销**——确认框会明确提示这一点，请只在确有此意时点 **强制拉取**。

## 预览将要拉取的内容

在 Explorer 右键 **Perforce ▸ 预览将要拉取的内容**。这是一次只读的预演（`p4 sync -n`）：不写任何文件、不改服务器。结果弹出一个列表，显示将要拉取的每个文件（文件名 + 动作 + 修订号，详情行给出 depot 路径）；选一个即可直接打开该文件。已经是最新时会提示 **已是最新版本**。

本地改了但没签出、拉取时会被跳过的文件也会列在这里，动作标为 **not updated** —— 它们确实落后，预览不会把它们藏起来。

适合在**拉取最新版本**或**强制拉取**之前先看一眼影响面。

## 拉取进度与取消

真正执行拉取时（无论从哪个入口），编辑器不再只靠状态栏转圈，而是在**通知区显示进度条**：

- 先显示「正在检查需要更新的内容…」，向服务器拿这次要更新的文件总数。拿不到总数时退化为**不确定进度条**（只显示已处理的文件数），拉取照常进行。
- 之后随 p4 逐个文件推进，显示 `已完成 / 总数 · 当前文件名`。
- 进度条带**取消**按钮；取消等价于旧的状态栏转圈取消——只中止这次拉取，已经落地的文件保留，随后照常刷新。

## 拉取的作用域

「拉取最新版本」**不会拉整个 depot**。无参执行时（状态栏「可更新」计数、命令面板），作用域是：

1. 若开启了[聚焦目录](../search-navigation/focus-folders.md)（`workspace.focusEnabled` 且 `focusFolders` 非空）→ 只拉聚焦目录；
2. 没开聚焦 → 只拉**你打开的文件夹**。

也就是说，拉取范围总是「你当前关注的那部分」，而不是 p4 client 映射的全部。游戏项目里 client root 往往映射着比打开的文件夹大得多的树，无差别拉全量既慢、还可能带下你根本不用的分支。聚焦目录配置变了，作用域会自动跟随。

> 在 Explorer 里对某个文件 / 目录右键拉取时，永远只针对**那一个文件或目录**（目录递归其子目录），不受上述作用域影响。

> 落后检查与「他人占用」扫描同样跟随这个作用域，见[性能与配置](#性能与配置)。

## 常见拉取错误

从 P4V 迁过来的用户最容易在这里卡住。拉取失败时，编辑器按原因分类给出引导：

| 看到什么（p4 原文） | 意味着什么 | 该怎么做 |
|---|---|---|
| `can't clobber writable file` | 目标文件有**未收集的本地修改**（改了但没签出），p4 拒绝覆盖，且**整次拉取中断** | 错误提示条里有 **收集改动** / **强制拉取** 两个按钮——想保留这些修改就先收集再拉；确定不要时点强制拉取（还有一次确认，会永久丢弃这些修改） |
| `can't update modified file` | 同样是「本地改了但没签出」，但你的工作区允许直接改文件（`allwrite`），所以 p4 只**跳过这一个文件**、仍然算成功，同一次拉取里的其它文件照常更新 | 提示条给 **收集改动** / **查看差异** / **强制拉取** 三个按钮，见[有文件被跳过](#有文件被跳过本地改了但没签出) |
| `must resolve` | 文件存在**未解决的冲突**，必须先合并才能拉 | 先[解决冲突](./resolve-and-advanced.md#冲突解决resolve)，再重新拉取 |
| `file(s) up-to-date` | **不是错误**：已经是最新版本（p4 习惯把它报到 stderr，编辑器会识别并提示「已是最新版本」） | 什么都不用做 |
| `no such file(s)` | 文件不在 depot 中，或不在当前 client 的视图映射内 | 检查是否用错了[工作区](./overview.md#切换工作区client)，或确认文件确实已提交 |
| 其它 | 未识别的 p4 错误 | 提示条显示 p4 原始输出；在面板标题栏 ⋯ 菜单选 **显示输出**，打开 **Perforce 输出**底栏看完整命令日志 |

> 「已是最新版本」只在 p4 真的这么报时才提示。若一次拉取既没更新任何文件、也没给出可识别的结果，编辑器会如实说「没有返回可识别的结果」并给 **打开 Perforce 输出** 按钮——绝不会把不确定的结果说成已是最新。

## 状态感知

### 资源管理器灰字

资源管理器里，Perforce 文件名后会出现灰色小字提示（由[后台扫描](#性能与配置)驱动）：

- **↓**：服务器上有比本机更新的版本。悬停显示具体动作与修订号（如 `edit #42`），用**拉取最新版本**即可获取。
- **✎**：有人正在改这个文件，悬停显示是谁（`user@client`）。对无法自动合并的二进制游戏资源来说，**「别人正在改」比版本号更重要**——动手改之前先看它。
- **✎ ↓**：两者同时成立时合并显示。

> 落后文件超过 500 个时不再逐个标灰字（几百上千行灰字没有可读性），只保留状态栏计数；日志里会如实记录这次跳过，绝不静默。

### 状态栏

> 这些条目只在源代码管理侧栏当前选中 Perforce 仓库时才显示；选中 Git 仓库时它们整体隐藏（Git 的分支条目同理只在选中 Git 时显示），避免混合目录里两套状态互相干扰。

Perforce 在状态栏左侧有三个条目：

1. **客户端名**（`client 名 N 个已打开`）：连接状态与已打开计数；p4 操作进行中会显示进度文案（**此时点击可取消该操作**），旋转图标固定在文案最右。平时点击打开 [Perforce 图谱](./perforce-graph.md)。扫描工作区（reconcile）进行时文案带计数，形如 `…branch_xyz: 3/12`——冒号前是工作区名（超过 10 字符时保尾截断、前置省略号，优先切在下划线边界），冒号后是 `已扫描目录数 / 已扫描 + 待扫描`；其余 p4 长操作（submit / sync / revert 等）没有计数，形态是 `…branch_xyz: Syncing…` 加右侧旋转图标。
2. **可更新计数**（`N 个可更新`）：落后文件数，只在检查跑过且确有落后时显示；点击先弹出「要同步到哪个变更列表」——第一项固定为**最新版本**（`#head`，等价于旧的整作用域拉取、一键可达），其后按新→旧列出本工作区尚未完全同步的已提交变更列表（最多 50 条，每条显示描述首行 / `@变更号 · 提交者 · 日期`，只同步了一部分的额外标「部分已同步」），若还有更早的变更（或列表为空）末项为「更早的变更列表…」可手动输入变更号；选定后同步 `<作用域>@<变更号>`。落后超过 500 个时显示「超过 N 个可更新」（计数此时是下限，且不再逐个标灰字）。
3. **当前文件版本**（`#have / #head`）：活动编辑器里那个文件的**本机修订 / 服务器最新修订**。落后时显示 `#have / ↓#head`，点击只拉取**这一个文件**；新加入 depot 的文件显示「新增」。悬停有完整提示。

> 扫描工作区时，`已扫描 / 已扫描 + 待扫描` 里的分母会在扫描过程中**增长**：扫描按广度优先的目录队列推进，遇到较慢的目录会拆成子目录重新入队，于是 `3/12` 可能变成 `8/25`，最终收敛到 `25/25`——这是队列在展开，不是进度倒退。悬停状态栏可看完整明细，无需任何配置：第一行补回完整工作区名，之后依次是已扫描 / 待扫描目录数、当前正在扫的目录（批次切换间隙可能不显示，位于工作区根目录时显示「工作区根目录」）、已发现差异文件数与已耗时（不足一分钟为 `12s`，超过为 `1m 12s`）；扫描可取消时末行提示「点击可取消」。

> 本地改了但没签出的落后文件同样计入这个计数、同样标灰字——它们确实落后，只是拉取时会被跳过（见[有文件被跳过](#有文件被跳过本地改了但没签出)）。

> 灰字与计数只在检查**成功跑过**时才出现——没显示不等于「已是最新」，也可能只是刚打开编辑器、还没检查过（或关掉了自动检查）。

### 被忽略的文件变暗

被 `.p4ignore` 规则排除的文件和文件夹，在资源管理器和编辑器标签页上会**变暗（灰色）**显示——和 Git 仓库里被 `.gitignore` 忽略的文件是同一套观感，见[资源管理器与文件操作](../editing/explorer-and-files.md#资源管理器在哪)。

几点值得知道：

- **只有本地文件会变暗**。已经在 depot 里的受控文件即使碰巧命中了忽略规则，也**不会**变暗——它已经被 Perforce 管着了，把它标成「忽略」会误导。
- 编辑 `.p4ignore` 后无需重启：保存即重新判定。但如果你用 `p4 set P4IGNORE=<自定义文件名>` 改过忽略文件的名字，编辑那个自定义文件不会自动触发重判，重开工作区或重载窗口后生效。
- 有本地改动、或带上面那些灰字提示的文件，仍按各自的状态颜色显示，不会被变暗盖掉。
- 一个文件同时归 Perforce 和 Git 管时（比如 p4 工作区里嵌了个 Git 仓库），用谁的忽略规则判定，取决于**源代码管理面板里当前选中的仓库**——切换选中项，变暗结果随之切换。

## 性能与配置

落后检查与「他人占用」扫描都是**后台低频**的：默认每 5 分钟一次，以后台优先级运行、绝不阻塞你的点击；每次拉取之后会立即重查一次，让计数马上反映新状态。

为什么是 5 分钟而不是实时：判断「哪些文件落后」需要把整个作用域与服务器逐一比对（`p4 sync -n`）。在约 45 万文件的工作区上，这条命令覆盖整个 client 根需要**超过 120 秒**——把它当实时检查会持续打满服务器。因此实际是两级设计：先查一条毫秒级的廉价信号（这个作用域里有没有新提交），**没有新提交就到此为止**；只有确实有人提交了，才跑一次真比对。安静的工作区里，贵的比对几乎从不执行。5 分钟一次是「滞后感可接受、服务器开销可忽略」的平衡点。

「他人占用」扫描读的是服务器的打开表——成本随团队的签出活动增长、与工作区大小无关，同样默认 5 分钟一次。

| 配置项 | 作用 | 默认 |
|---|---|---|
| `perforce.syncPreview.autoCheck` | 后台落后检查 + 灰字 `↓` + 状态栏计数。**超大型 depot 建议关闭**，改为按需用「拉取最新版本」（拉取后仍会立即重查一次） | 开 |
| `perforce.syncPreview.intervalSec` | 两次落后检查之间的最小间隔秒数（最小 30） | 300 |
| `perforce.openedByOthers.autoCheck` | 后台「他人占用」扫描 + 灰字。在非常繁忙的共享服务器上可关闭 | 开 |
| `perforce.openedByOthers.intervalSec` | 两次「他人占用」扫描之间的最小间隔秒数（最小 30） | 300 |

> 关闭自动检查时，已有的灰字与计数会**立即清空**，而不是留下过期的提示。

> 什么时候该关：落后检查真正的开销全在那条全量比对，而它只在「有新提交」时才触发。如果你在一个超大 depot 上工作、且频繁有人提交，可以关掉 `perforce.syncPreview.autoCheck`，靠手动拉取 + 拉取后的自动重查来了解落后情况。
