# 收集修改（常驻 reconcile 分组）与 Explorer 按需徽标通道

> 本文是 `extensions/perforce/CLAUDE.md` 的配套详情档，讲「收集修改」体验对齐 git 的完整实现：常驻 reconcile 分组、Explorer 行级改动徽标（`checkWorkingTree`）、落后灰字（`checkBehind`），以及它们共同的边界——**工作区范围（daily scope）**。

## 工作区范围（daily scope）：唯一来源是配置文件，编辑器自己解析

**范围的唯一持久来源**是 **client 根目录下固定位置**的 `.p4delta-scope`（JSON；不再沿上级目录链查找）。编辑器与 δ **各自解析同一份文件**——两侧是同一契约的两份实现（语言无关的行为向量共用 `src/__tests__/fixtures/scope-contract.json`），**没有运行时握手**：没有请求文件、没有快照、没有回显、没有指纹、没有 token / TTL。范围因此不需要任何进程参与：`src/scopeConfig.ts` 严格解析 JSON，`src/scope.ts` 算集合代数，`PerforceClient.refreshScope()` 一次本地读 + 一次纯计算就得出本轮范围（`ScopeView`）并 `_applyScopeBase` 把派生量（默认 get 的 `_syncScopes`、命令层预检用的排除目录、检查点指纹）一次落地。

配置形状：`include` / `exclude` 两个数组，条目恰好一个 **`{"dir": "相对路径"}`**（整棵子树）或 **`{"file": "相对路径"}`**（精确这一个文件）——**类型由写出来的键决定**，不 stat、不按本地存不存在猜。省略 `include`（或整份写成 `{}`）＝整个 client root；**`include: []`** 是**明确的空集**，与「没写」不是一回事。路径是 client root 相对的 `/` 拼法（反斜杠、绝对路径 / 盘符、`..` 越出 root、`...`、`*` `?` 通配符一律报错）。空正文 / `null` / 错类型 / 未知字段 / **重复键**一律报错——一条被静默丢掉的 `exclude` 会让范围**放大**，正是这套契约 fail closed 的方向。

「client 根目录」指的是 client spec 里**固定的 `Root`**，不是 `p4 info` 报的 `clientRoot`——后者按 cwd 回答，打开目录落在某个 **AltRoot** 里时报的就是那个 AltRoot，它不是这个 client 的范围归属（那棵树上多半没有 `.p4delta-scope`，读成「没有配置」就是把范围悄悄放大到整棵树）。两侧各自封住这个口子：编辑器在 `clientDiscovery.ts` 里把发现到的根与 `p4 -c <client> client -o` 的固定 `Root` 核对，**能证实的 AltRoot 一律拒绝**，**读不出来的 spec 也一律拒绝**——非零退出、没有 `Root` 字段、或字面 `null` 都算读不出来，此时报来的根**未被证实**（可能正是 AltRoot），采信它就是在猜 client 的根，而猜错的代价正是「在别人的树上把范围读成没有配置」，所以一律失败关闭：provider 对这个目录不启用并打一行 `provider disabled` 日志（`verifiedClientRoot`）；δ 一律先读 spec 的固定 `Root` 为权威（见其 `resolve_client_root`），cwd 停在 AltRoot 上直接失败关闭。

范围代数（`resolveScope`，与 δ 的 `combine_scope` 逐条对齐）：**include = 配置 ∩ 目标**（配置没写 include 时它就是 client root 本身）；**exclude = 配置 ∪ 本操作自己的排除项，无条件优先**；**生效的配置文件自身是隐式 file 排除**（对 `p4 clean` 就是「别删用户的范围配置」，对收集就是「别把它报成待新增」）。

四态（`ScopeState`）：

- `unresolved`：本会话还没算过；
- `ready`：有可用范围。**没有配置文件（ENOENT）不是错误**——范围就是打开的工作区（client root 内没有额外限制），原生能力一个不少；
- `empty`：合法但为空的范围（含 `include: []`）——「范围内什么都没有」是**结论**，绝不是放开到整个 client 的理由；
- `blocked`：配置文件**在那儿但读不了 / 非法**——权限不足、不是普通文件、超 1 MB、非 UTF-8、JSON 或语义错误都算。此时日常操作（发现 / 收集 / 清理 / 普通拉取）全部拒绝，`extension.ts` 弹 `perforce.scope.blockedNotice` 并带上 `scopeUnusableReason`。**只有 ENOENT 才是「没有配置」**；其余一律不能被读成「没有约束」。

四态与 δ 是否可用**无关**（`_computeScope` 只读文件）：引擎不在时范围照样解得出来，只是那几个操作退回 p4 原生执行。

**排除项怎么到达引擎**：δ 自己读同一份配置文件，编辑器**不把配置的排除项抄进 argv**——一份会过期的副本足以与磁盘上的文件意见相左。argv 上只带**本操作自己的**排除项（收集降噪，见下节），拼成 `--exclude-dir <绝对路径>` / `--exclude-file <绝对路径>`，**类型由旗标表达**，一个目录规则不可能被读成文件规则。

**用户点名的目标不被静默裁剪**（`confirmScopeTargets` → `client.checkScopeTargets`）：未被范围**完整**覆盖的目标（`scopeCoversTarget`：整条坐在某个 include 里，且没有任何排除项碰到它）会被弹框点名，两个按钮——「遵守工作区范围」丢掉未覆盖的（丢完为空则**不执行**该操作：空范围是另一件事，不是更小的那件事），「按所选执行」为**这一次调用**打开 override。override 的形态就是 δ argv 上的 **`--no-scope-file`**（这一次不读配置文件，范围 = 目标 ∩ client root），**只由这个按钮产生**；编辑器的本地判定在同一调用里同步放宽（`WriteOptions.overrideScope` → `_writeRangeTargets` 跳过与范围的求交、`_carveDirs` 不再带上范围的排除项、`_deltaWrite` 的 override），所以「按所选执行」不会被自己的 fail-closed 检查拦下。同一个 spec 里的其它目标不因此获豁免——override 是**整次调用**的属性，不是「以后都算数」。

**范围 / 聚焦 / 降噪是三层，互不推导**（见下文「扫描范围」与「收集降噪」）：范围是**日常**边界，聚焦只收窄自动发现，降噪只让收集类界面别看见；三者唯一同时出现的地方是扫描（`scope ∩ focus − noise`），其余操作各有各的边界。

**范围什么时候重解析**：编辑 / 新建 / 删除范围文件 → 配置 watcher → `invalidateScope()`（丢漂移行与检查点、防抖后重新 `refreshScope`——静默失效会让一个刚坏掉的配置变成「什么都不报、也不说为什么」）。每次操作按**执行那一刻**的磁盘内容算：一次操作里的预览与随后的执行各算各的，中间改了配置文件，执行用的就是**新**内容。**没有「配置变了就拒绝」这一档**：那需要一个冻结的旧计划作为对照，而这里从头到尾只有磁盘上那一份——两侧（编辑器与 δ）读的都是当前文件，用户确认的范围就是磁盘上的范围（`_deltaWrite` 的头注释是这条的出处）。不给冻结计划配一句提示的做法已废止：预览→执行之间真的变了**会**说一句（下一条），但那仍然只是一句话，不是对照、不是拒绝。

**四个 δ 执行点各有自己的 argv 拼装**（扫描 `_buildP4deltaScanArgs`、窄查 `_buildP4deltaNarrowArgs`、写操作 `_buildP4deltaWriteArgs`、普通 get 与预览 `_buildP4deltaSyncArgs`），共同形态是「`--json --client-root <root>` + 契约开关 + 本操作自己的 `--exclude-*` + 位置目标」，细节见下文各条；**没有 `-- <条目>` 这种位置排除形态**，调用点想漏也漏不掉。

**预览是提示，不是契约**：`previewSync` 与随后的 get 是**两次独立调用**，各自解析当时的配置与目标，不共享任何 token / 临时文件（旧的 `holdOperation` / `adoptVerified` / `scopeToken` 已随范围协议一起删除）。所以「预览之后、执行之前改了配置」不会拒绝，也不会拿旧计划重放——它按新内容执行，重新预览一次看到的就是同样的清单。唯一的遗迹是**一句提示**：`previewSync` 收口时把 `{spec, scopeIdentity}` 记成一条一次性便签（`_recordSyncPreview`；被拒 / 失败、没收口的预览什么都不记），紧随其后的 get 在执行入口比对（`_noteSyncPreviewDrift`，紧跟 `_ensureScopeResolved`）——身份变了就弹 `perforce.sync.previewConfigMoved`「本次按当前配置执行」。它**只提示**：不拒绝、不延迟、不重放，并被下一次 get 消费（一次预览只对着一次 get）；身份没变、spec 不同（那是另一次 get）、范围当前不可用又没有 override 时都静默。身份用 `scopeIdentity`（范围自身归一化后的摘要，**刻意不含降噪**），所以改 `perforce.reconcile.excludeFolders` 永远不触发它——默认 get 本来就不读降噪。

## 收集降噪（`perforce.reconcile.excludeFolders`）——与范围完全无关的另一层

范围回答「哪些路径属于我的工作」；这个设置只回答「收集类界面别再看见哪些路径」。两者互不推导：降噪**既不放宽也不收窄范围**，范围也不因为一个目录被降噪就不再是范围的一部分。

- **读入与热更**：`extension.ts` 的 `applyReconcileExcludes` 在激活时、以及 `affectsConfiguration('perforce.reconcile.excludeFolders')` 命中时读设置（精确键；订阅要点见根 CLAUDE.md），经 `reconcileNoise.ts` 的 `resolveReconcileExcludes` 解析成绝对本地路径（相对 = 相对工作区根、嵌套折叠；**凡 stat 不出目录身份的条目一律当目录收**——`stat` 答 `isDirectory:false` 的既有文件才是 file 规则。设置名是 folders，而「先配置、后建目录」是常态：按 file 收会把该子树冻成「不排除」，等目录出现后扫描会发它的行、`clean -a` 会删里面的文件，那个方向不可恢复），交给 `client.setReconcileExcludes`；`switchClient` 的 wiring 也要带上它（新 client 与已有 client 必须拿到同一份规则）。`setReconcileExcludes` **刻意不是 `invalidateScope`**：日常范围与同步账本一个都不动，只有收集侧答案（漂移行、扫描检查点、discovery 代次）随它走，并调 `_resetReconcileScanForScopeChange()` 让扫描按新集合重新预热——改这个设置与改范围文件互相看不见对方（预览本来就只是提示：它之后的 get 在**执行时**重新解析范围，见本文开头）。
- **作用面**：后台收集扫描、窄查（`checkWorkingTree` / watcher 增量）、收集 / 收集到指定 CL / 清理（未签出的那一半）。**普通 get 不带它**——它的范围是日常范围自身，把降噪目录里的文件照样拉到目标版本（这是「降噪不是范围」最容易被搞错的一处，`perforceReconcileNoise.spec.ts` 里有专门的旅程钉它）。
- **传输形态**：作为本操作自己的 argv 条目随 δ 调用走——`--exclude-dir <绝对路径>` / `--exclude-file <绝对路径>`（`noiseExcludeArgs`），**类型由旗标表达**；δ 把它与范围文件自己的排除**取并集**（配置 ∪ 调用方，排除无条件优先，配置文件自身的隐式排除排在最后），编辑器则不把配置的排除项抄进 argv（它自己读同一份文件）。规则由 **client 在写入那一刻**从当前设置读（`currentReconcileRules(confirmedTargets)` → `noiseFor`），命令层只交「用户点名的那些目标」，**不交规则副本**——一份调用方读好的旧副本会压过更新的设置（「确认期间新加的排除管不住这一次 clean」的来路正是它）。**没有冻结、没有规则戳**：「确认框到执行之间规则被改」不会换一份规则在跑，也不会被拒绝——两侧都在**那一刻**读当前设置，用户确认的就是当前这一份。
- **δ 还是原生**：判据 `_p4deltaEngine()`（δ 已在本会话被证明能答这个工作区）与「这组目标能否原样交给 δ」（`canHandTargetsToP4delta`：不含 `[@#*%;]`）**都在 `_mutateWrite` 里、落在同一份读数上**当场问；命令层不再预判引擎——`reconcileUsesP4delta` 只是给命令层与测试观察的只读开关，**绝不参与任何决策**（在确认框之前读它一次、按它把目录 carve 成 `<dir>/*` 正是要消灭的做法：那会把 disarm / 重配窗口里落到原生的调用直通 δ 的宽目标）。δ 可用时这次调用一次带走排除项、位置参数是**原始 targets**（排除项由引擎在同一调用里应用，调用点不 carve）；落到原生分支时 spec 列表在这一刻才从原始 targets 现算：`_writeRangeTargets` 先与**当前**范围求交，`_nativeCarveReject` 复核（范围一半 + `_nativeFileExcludeReject` 的不可表达缺口一半，命中即拒绝、两个引擎零 spawn），`carveReconcileTargets` 再按**当前**排除集 carve（红线：绝不退化成 `<dir>/...`）。`_carveDirs` 的排除集 = 「范围自身的 exclude（override 时不计）+ 本操作的降噪」并集，两者都在执行那一刻读；范围文件自身的排除由 δ 自己读同一份文件，编辑器**不抄一份进 argv**。
- **明确点名的目标不静默**：`extension.ts` 的 `confirmNoiseTargets` 对「用户直接选中、且被降噪覆盖」的目标弹「跳过它们 / 按所选执行」——跳过则一个 p4 进程都不 spawn（提示「所选路径在工作区范围之外，或被排除规则隐藏。」），按所选执行则为**这次操作**构造只含所选目标、不带该规则的策略（`planReconcileNoiseOperations`；规则在执行那一刻读，不再有「报告后规则再变即拒绝」这一档）；同一批里的**祖先目录**仍按普通批量静默裁剪（执行入口的 carve / δ 排除），只有被明确点名的那个目标获得豁免。

## 收集修改（常驻 reconcile 分组）

**根因**：git 面板 = 磁盘真相（`git status`），p4 面板 = 服务器 `p4 opened`（只显示**已签出**的文件）→ 磁盘上改了/建了/删了但没签出的文件面板看不到，形成「改了看不到、想签点不到」死结。解法是一个**常驻分组** `_reconcileGroup`（`RECONCILE_GROUP_ID = 'reconcile'`，SCM 组 id，标题「Changes」，与 git 的 Changes 组同名以省出横向空间），它的 `resourceStates` = 未签出但磁盘偏离 depot 的全部文件，**整组可见、可点、可拖**，让 p4 面板对齐 git 的「Changes」体验：

- **常驻组成员**：`client.ts` `_reconcileGroup` 在 `_resolveGroup` 之后、changelist 组之前创建（`createResourceGroup`），所以渲染在「Needs Resolve」之下、changelist 组之上（SCM 视图按创建顺序显示组）；`hideWhenEmpty = true`，无漂移时整组消失。
- **组内容 = 全量替换，不是 patch**：`_applyDriftGroup()` 是**唯一**写 `_reconcileGroup.resourceStates` 的地方，且**每次赋整个数组**。全量替换是承重设计——renderer 从新数组整体重建文件/文件夹装饰，**离开集合的行连带它的文件夹染色（含祖先）一起回收**；逐行 patch 会把我们打回文件夹聚合的老路。行过滤（已 `opened` / excluded / scope 外）在赋值处而非合并处跑，所以「收集一个文件」下次刷新就自动移进它的 changelist 组，无需重新扫描忘记它。
- **数据源**：`_driftFiles`（`Map<key, ReconcileFile>`）。发现走**单轮扫描 + watcher 增量**——每个会话一次穷举扫描（`scheduleReconcileScan`，`_rescanReconcilePaths` 按目录分批喂入），之后靠 `_startExternalWatcher`（`watchRoot` + `createFileSystemWatcher`，见 `extension.ts` 传的 opts）逐文件增量修正。任何会改 `_driftFiles` 的路径都走 `_scheduleDriftApply()` 合并赋值（窗口随行数缩放）；扫描轮末 `_flushDriftApply()` 同步落定，面板与「scanning x/y」后缀同 tick 收敛。
- **扫描引擎按会话择一**：`runReconcileScan()` 先 `refreshScope()` 拿日常范围——**范围不是 `ready` 就什么都不扫**（不可用的范围绝不扩大成整个工作区）——再算 discovery = 范围 ∩ 聚焦（`scopePartsWithin(base, focusTargets)`，见下文「扫描范围」条），然后只做分派：本会话解析到 p4delta 可执行文件（决策在 `extension.ts` 的 `resolveP4deltaEngine`：路径存在即用，缺文件记一行日志回原生；`perforce.p4delta.*` 配置只在那里读，客户端只收 `PerforceClientOptions.p4delta`）就**一次 δ 覆盖整个 discovery**（`_buildP4deltaScanArgs`：`--json --client-root <root> --no-revert-groups [--exclude-dir/-file …] <targets…>`；排除项是本操作的降噪，范围文件的排除由 δ 自己读同一份配置），否则走原生 `_runNativeReconcileScan`。两者共用同一套漂移集 / 进度 / checkpoint 管线，差别只在 checkpoint 键的指纹带引擎标记（`native`/`p4delta`），互不串读。**失败的五种形态一律「无结论」**（`_p4deltaRunFailure`）：没有 summary（被杀/崩溃）、stdout 出现非 JSON 行、exit 2、`ok:false` 且 reason 不是 `no-entry-matched`、以及 **summary 的 `mode` 不是 `open`**（另一档模式的记录集不是本轮的答案，读它会发布并 checkpoint 一份没人问过的快照）——**扫描这一档同轮回退原生**，失败绝不许读成「没漂移」；`no-entry-matched` 则是**完整答案**（不是失败）。用户取消与连接断开不算失败。连续 3 次失败本会话 disarm（只记一条日志，之后一律原生，只有 `setP4delta` 重新配置才解除——改 `perforce.p4delta.*` 会清零计数、把扫描引擎判定退回 native）。δ 的 `{kind:'progress'}` 阶段只用于状态栏与组标题文案（不再显示伪造的「已扫描 N 个目录」）。δ 分支的 per-file 收尾照原生语义读本轮的 `completed`：被取消/dispose 打断时既不 flush 也不打 "complete"（那会让日志声称一轮根本没走完的扫描已完成）。**回退阶梯红线：扫描与窄查对同一形状必须给同一个答案，判定表因此只有一份**（`client.ts` 的 `p4deltaContractFailure`，扫描与窄查都经它）：`handoff`（δ 转交原生 p4 的文件、没给出它会采取的动作）在两条路径上都判「无结论」——δ 违约时扫描据此同轮回退原生，既不把 handoff 读成「无漂移」，也不为它写 checkpoint（那会让一次拒绝在下一轮以「答案」的身份回来）。
- **窄查跟随扫描选定的引擎**：`checkWorkingTree` / watcher flush / `revert -k` 补查 / sync 后重验都经 `_rescanReconcilePaths` 的 per-batch，即 `_narrowQueryBatch`——同一会话沿用**扫描已选定并验证过**的引擎（`_p4deltaEngine()`：`_reconcileScanEngine === 'p4delta'` 且未被 disarm，不是「配置了 δ 就用」；首次扫描前、disarm 后、以及每次 `setP4delta` 重新配置之后都是原生——那份「δ 能答这个工作区」的证明属于跑到它的那个二进制，换了 build 就得重新扫一轮才恢复）。δ 下一批一次调用（`_buildP4deltaNarrowArgs`：`--json --client-root <root> --no-revert-groups [--exclude-* …] <targets…>`，无 `-a`），批次路径经 `targetsFromSpecs` 变成**类型化 targets**（编辑器的 `<dir>/...` 由 `entryFileSpec` 拼出，这里只读回同一个形态），排除项由引擎在同一次调用里应用，所以 δ 分支**不 carve**（`_narrowQuerySpecsFor`：目录直接给 `<dir>/...`）——但**仅当整批路径都能表达成本地 targets**（绝对本地路径、不含 `@#*?%` 元字符、不是 `//` depot 拼写），否则该 spec 照旧 carve、由拆批路由回原生；原生分支一字未动。判定沿用契约硬条款：无 summary / 非 JSON stdout / exit 2 / **summary 的 `mode` 不是 `open`** / `ok:false` 非 `no-entry-matched` / 出现 `handoff` 记录 → `undefined`（无结论）——该批路径**保持原有漂移、不进 covered**（绝不读成 clean），且**不做同轮原生重跑**（窄查太频繁；扫描才同轮回退），失败与扫描共用同一架三振梯子；`no-entry-matched` 是完整答案（该批路径算 covered，静默即结论）。**不可读的 spec 按 spec 拆批**而不是整批二选一：carve 产物（`<dir>/*`、被转义的元字符）必须原生，而同一批里 δ 形态的 `<dir>/...` 一旦被拖进原生就会**越过它的排除项**（排除项只随 δ 调用走）——所以 `_narrowQueryBatch` 把不可读的 spec 交给 `_reconcileScanBatch`、其余交给 δ，两边 `files` 合并、`partial` 取或、**任一边 `undefined` 则整批 `undefined`**（半份答案不许把另一半没答过的路径记成 clean）。这仍是路由不是健康判定，不碰三振梯子。
- **写操作同样跟随那一份判据**（`_p4deltaEngine()`；`reconcileUsesP4delta` 是给命令层与测试的只读观察开关，**不参与决策**）：`reconcile(paths)`（收集）、`reconcileInto(cl, paths)`（收集到指定 CL）、`revertReconcile(paths)`（清理，对应原生 `p4 clean -a -e -d`）在 δ 可用时各走**一次** δ 调用（`_buildP4deltaWriteArgs`：契约开关 + 模式（`--clean`）+ `-c` + `-a` + `[--no-scope-file]` + 本操作的 `--exclude-*` + 位置 targets，**没有 `--` 位置条目**）。三处共用 `_mutateVia` 骨架（`_mutate` 也拆成它的一次调用，签名与三条出口一字未变）：成功 = `summary.ok === true` **且 `summary.applied === true` 且 `summary.mode === 本次请求的模式`**（`reconcile`/`reconcileInto` → `open`，`revertReconcile` → `clean`）——只看 `ok` 会把「记录齐全、`ok:true`、`applied:false`」的预演形状流读成「已经收集/清理完成」，进而 `_invalidateAfterMutation` 删掉漂移行让面板显示已处理，而磁盘/服务端根本没变（`no-entry-matched` 在写操作里**算失败**——用户点名要动的路径一个都不存在，该说的得说）；失败走同一个失败 toast（δ 的 `summary.reason` + stderr 尾部合成 `P4ExecResult`）与同一架三振梯子（满三次 disarm，本会话之后全原生）。**失败绝不回退重跑原生**——与扫描的「同轮回退」不同：`-a` 可能已经改了一部分状态，换一份实现按自己的读法重跑，两个方向都可能做过头，`--clean` 更是不可逆；用户拿到 toast，下一次操作自然落回 p4。取消（`signal.aborted`，含 dispose 的 abort）不算失败、不计数、不 toast。**退回原生的守卫**（不计数、静默走原生）：整组路径表达不成类型化 targets——p4 filespec 元字符（carve 产物 `<dir>/*` 正好命中）、`//` depot 拼写。这条**不是**需要命令层互补的一道安全网：原生分支本来就从原始 targets 现 carve（见下条），「未 carve 的 δ 形态漏进原生」这个形态已不存在。
- **命令层不再 carve，只交「原始 targets + 明确授权」**：全部写操作（收集 / 收集到指定 CL / 清理 / 重开进 CL）都只调 `client.reconcile({ targets })` / `reconcileInto(cl, { targets }, options)` / `revertReconcile({ targets }, options)`——carve 与 δ 形态**全在 `_mutateWrite` 一次构造**（见上条）。命令层送出的授权只有两条，都是「用户刚做过的决定」：`confirmedTargets`（用户在降噪确认框里点名的那些目标；`planReconcileNoiseOperations` 按目标把它们分好组）与 `overrideScope`（「按所选执行」）。规则副本不再随调用走，client 在写入那一刻读当前设置，只把覆盖**那些点名目标**的规则 lift 掉。**这次变更的核心就是把 carve 从确认框之前挪到执行入口**：从前 `p4 clean` 的 carve 在确认框**之前**完成，而 clean 在用户点下按钮之后才跑，中间隔着一整段人机时间——那期间改了配置文件，旧实现只复核「范围此刻仍可用吗」，产物仍是旧规则下的（这是范围不再是 δ 协议之后原生侧留下的人机缺口，现已消除）。执行入口按**那一刻**的范围与排除集现算，用户确认的就是「按当前规则执行」这件事本身（文案见 `perforce.revert.confirmCurrentRules`）；确认期间改了配置仍然按新配置执行——不重建协议、不强制重预览、不自动拒绝，因为这里没有任何旧计划需要对照。
  - **「按所选执行」的豁免不外溢**：`overrideScope` 是**整次调用**的属性，但它只放宽范围那一层（`_writeRangeTargets` 不求交、`_carveDirs` 不带范围排除）；本操作的降噪 **不随之被 lift**，仍在 `_nativeCarveReject` 与 carve 里生效。只有 `confirmNoiseTargets` 对「用户明确点名且被降噪覆盖」的那一个目标留下授权（见下条）——同一批里的祖先目录 / 兄弟 / 嵌套的未授权排除照常按当前规则处理，豁免绝不扩散。
  - **越界目标不许静默变窄**（这道 gate 答的是**范围**）：命令层先经 `confirmScopeTargets` → `client.checkScopeTargets(targets)` 拿 `inside`（范围 ∩ targets，即「遵守范围」会跑的东西）与 `outside`（被范围 / 排除项整块吃掉的目标）；有 `outside` 就弹「遵守工作区范围 / 按所选执行」——前者丢掉未覆盖的（丢完为空则不执行），后者这一次调用带 `--no-scope-file`，范围变成 client root ∩ 用户刚选中的那批（见本文开头的范围节）。「整条路径被排除」（`isReconcileTargetExcluded` / `notifyAllExcluded`）与「路径下有被排除的子树」（client 的 carve）是两回事：前者范围 gate 也不放过，后者由执行入口的 carve 处理。
- **普通 get 走 δ，force / δ 表达不了的 spec 保持原生**：δ 的 `--sync`（不带 `--force`）就是 `p4 sync` 语义——先 `p4 -G sync -n` 预演，把保护 / opened / resolve / have 全交回原生判定，自己只把候选按 `//depot/file#rev` 的精确规格交回 p4 apply，所以编辑器的默认 get（`#head` / `@<CL>`）映射过去**不丢任何本地改动**。写法：`_buildP4deltaSyncArgs` = `--json --client-root <root> --sync [--to <CL>] [-a] [--no-scope-file] <targets…>`；目标**不是**编辑器算好的范围：调用方点名的 scope 原样交出去，而无 scope 的 get 交的是**打开的工作区**（硬上限）——δ 自己读 client root 的同一份配置再求交（`_p4deltaGetTargets`；传一份旧读取算出的 include 列表等于偷偷换掉范围），**不带**降噪排除项（降噪不是范围），**不带** `--parallel`（`perforce.syncParallelThreads` 只对原生生效，>0 时记一行日志）；`previewSync` 同走 δ 但不带 `-a`。
  - **资格判据**（`_p4deltaSyncReject`，返回原因即走原生）：spec 只能是 `#head` 或 `@<纯数字 CL>`（`#<rev>` / `@<日期>` / per-file force 的 `''` 都是 δ 范围语法读不懂的形态）；`force === true` 一律原生（它的 spec 是被拒文件钉死的 `#rev`，且这正是用户刚确认过覆盖的那条路，最不值得换引擎）；entries 非空、不得是 `//...`（整 client），并且**整组要能表达成类型化本地 targets**（`targetsFromSpecs`：绝对本地路径、不以 `//` 开头、不含 `[@#*?%]`；调用方直接点名的类型化目标不受元字符限制——δ 在 p4 边界自己转义，`50%_stuff` 这种名字照样走 δ），否则整发 get 落到原生。
  - **无版本门槛**：解析到 p4delta 可执行文件即启用（`resolveP4deltaEngine` 里只做一次 `existsSync`）。这里以前靠一次 `p4delta --version` 采样把 < 0.1.6 的构建整个挡在门外——那些构建的 `--sync` 是强制修复，喂给普通 get 就是丢用户工作。现在按「p4delta 支持全部功能」的前提去掉了这道闸，**有意接受的后果**是：路径上真的是旧 build 时它会被驱动，防线只剩契约硬条款（summary 缺 `ok`/`mode`/`applied` 或 `force` 为真 → 无结论、回退原生）——那只兜得住「旧 build **自报** `force`」这一形态，不是对真 0.1.5 的保证。
  - **记录 → `SyncRunResult`**（`p4deltaParser.toSyncOutcome`，纯函数）：summary 必须 `ok && mode==='sync' && applied` 且 `force` 不为真，否则**无结论**（`force` 与 `applied` 同为「只有显式 true 才算」）；`class: add|update|delete` → `applied` 计数 + `appliedFiles`（`action` 优先取 `nativeAction`）；`class: resolve` → `keptOpen` **与** `mustResolve` **各 +1**（原生对「已打开、have 不在目标版本」的文件同时打印 `is opened and not being changed` 与 `must resolve #N` 两行，δ 把这对收成一条记录，只加一个计数器会让 Resolve 按钮与 `recordSyncPoint` 的 complete 判定一起错）；拒绝行从 δ 的 stderr（p4 的 severity<3 提示被原样转写）用既有 `parseSyncRefused` 解析；`upToDate` = 三类计数与两个拒绝列表全空，`unrecognized` = 有 ok 结果却什么都没解析出来。
  - **三条只有上游源码才说得清的事（已对着 `p4delta` 源码 + 真实 build 核过，别按直觉改）**：① **候选为空时 `-a` 照样发 summary**——`run()` 把 `run_once()` 包起来，任何返回路径（含「No files to sync」早退）都发一条，`applied` 记的是「这轮带没带 `-a`」而不是「动没动文件」，所以「已是最新」是一条**结论**（`total:0` + upToDate），不是失败回退；② `--to <CL>` 由 `scope.query_specs` **钉在每一条入口上**（本地路径与 depot 子树一视同仁，漏掉哪条哪条就跑到 head），fake 的建模与之一致；③ 普通同步**永不发 `handoff`**（那只有 open/clean/force 走的 reconcile 管线才发），所以记录映射里 handoff→无结论 是防御性分支，真机上到不了。
  - **失败分层**：`stage:"apply"` 记录或 `phase:"apply"` 进度是「已开始写盘」的唯一证据——**没进 apply**（一个字都没写）→ 记一行日志、**同一轮回退原生**（纯收益）；**已进 apply** → **不回退**（换一份实现重跑两个方向都可能做过头），合成 `P4ExecResult` 交 `classifySyncError`（clobber 分支与各 toast 照旧）并计入三振梯子（回退掉的不计）。取消沿用 `_cancellable`，用已收到的 apply 记录做 `_removeDriftForSyncRun`——这一处**额外要求 `stage === 'apply'`**：契约说 `-a` 只发 apply 段记录，而这正是唯一一个「读错会**藏起**用户本地改动」的读者（把预演记录当已落盘，就会删掉那条文件的漂移行），所以它核对而不是假定。
  - `revert` / `revertChangelist` / `revertUnchanged` / `submit` / `reopen` / shelve 系 / `edit` / `add` / `delete` 仍然保持原生（δ 没有对应模式）。
- **Bug D 的两条失效路径都已堵**：watcher 删除磁盘路径（`_onExternalFileEvent` → `_flushExternalChanges` 的窄查询 + checkpoint 合并），以及超出 `MAX_EXTERNAL_NARROW_PATHS` 预算的命名空间擦除路径（`_invalidateAndLatch`）。都不得回退成「重新打开又全量重扫」——启动快照（checkpoint）持久化仍在，只是这两条路径不再摧毁它。
- **每个 watcher 路径按三态回答**（`_pathKind`：`dir` / `file` / `gone`，`_narrowQuerySpecsFor` 造 spec）——原实现把「`stat` 抛错」直接当成**被删除的文件**，于是删掉一个目录只发出 `reconcile -n <目录裸路径>`，而**裸路径永远是单文件 spec**（真机实测：exit 0 + 空 stdout + `<path> - no file(s) to reconcile.`），答案被读成「查过且干净」，子树的删除整个丢失。判据落成三条：
  - `file` → 只问裸路径（成本红线，不带 `/...`）。
  - `dir` → `<dir>/...`（`...` 展开按 depot/have 列表做，**与磁盘上目录是否存在无关**）。目录事件也走这条：目录被改名/移入工作区时同样只有一条目录级事件，其内容否则本会话不显示。
  - `gone` → **成对**发 `[<path>, <path>/...]`：裸 spec 覆盖「删的是文件」，`/...` 覆盖「删的是目录」，两者互不污染（真机实测混合批仍 exit 0 且正常返回 delete 记录）。
  - **原生下**含 exclude 子目录的路径一律走 `carveReconcileFilespecs`，**绝不退化成 `<dir>/...`**（红线同上文扫描）；carve 返回 undefined 时该路径只做 `_invalidateAndLatch`（本会话不显示，与修复前一致），日志记录退化。δ 下只有**路径不含元字符**时免 carve（排除项由引擎在同一次调用里应用，见上文窄查条）；含元字符就照走 carve，产物由拆批路由到原生。
  - 归属靠 `isUnderAnyKey`：`<dir>/...` 的答案回显的是**文件**路径，与请求的目录路径对不上，未精确命中的行按「是否落在某个子树查询下」认领并 `respellUnderRoot`。
- **`covered` = 被问路径 ∪ 返回行路径**（不只是行）：`_flushExternalChanges` 把 `covered` 写进 `_externalPatchedPaths`，而扫描轮 settle 时按**字符串精确比对**决定是否 `_invalidateReconcileScanFor(path)`——被问路径缺席会白丢覆盖它的父 checkpoint（下次开工作区全量重扫）。目录路径在下游两处消费都是空操作，留着无害。
- **`partial` 不再读作 clean**：`_rescanReconcilePaths` 现返回 `{files, failed, partial}`，超时批没返回行的路径既剔出 `covered`（不写 checkpoint）又保留其既有漂移行（**行是下界，沉默不是结论**）；`_reconcileScanBatch` 的 stderr 分支不再丢 `res.records`——判据是「无行 = 干净（checkpoint 行为不变），有行 = 至少一个 spec 被拒，绝不 checkpoint」。这条是新路径的必要条件：新入桶的批含一个匹配不到的裸 spec，旧写法会把 `/...` 吐出的真实 delete 记录整批丢掉，等于在新路径上复刻同一个 bug。
- **收口**：`_applyDriftGroup()` 同时维护 `_driftShown`/`_driftTotal` 与 `_updateDriftGroupLabel()`（截断 `perforce.reconcileLimit` 默认 10000、扫描进度后缀），二者都是**进度/截断提示，绝非装饰**——scan 逐目录推进而非一次原子落地，不带后缀的部分列表会被当作完整列表，用户会以为看全了。δ 在跑时组标题与状态栏同源：`ScanProgress.phase` 存在就用阶段文案（`scanPhaseOrdinal`，「scanning done (5/5)」），绝不把阶段序数印成「scanning 5/5」——那两个数在 δ 下不是目录数，native 下才是。
- **收集**：`reconcile(paths)`（explorer 右键「收集改动」`perforce.reconcile`，目录转 `<dir>/...`）跑**真**的收集——原生 `p4 reconcile -a -e -d`，δ 下走 δ 的 open 模式（见下文写操作条）——文件签出进 changelist。`reconcileInto(cl, paths)`（`reconcile -a -e -d [-c <cl>]`，`default` 省略 `-c`）把未签出文件直接收集进指定 changelist——供把未签出文件拖到 changelist 组头（`reopenTo`，见下文）。
- **移出 Changelist**：`moveToReconcile(paths)` = `p4 revert -k`（退出签出、磁盘内容保留），之后该文件出现在「Changes」组并在资源管理器显示改动徽标（M/A/D），可再收集回任意 changelist。**它必须自己把这些行加回漂移集**（`_reapplyDriftForMutation`：与 watcher 同一个 `_pathKind` + `_querySpecsFor` 造 spec——目录**以及已从磁盘消失的目录**都补 `/...` → 窄查一次 → upsert 进 `_driftFiles`/`_driftWatchedKeys` → `_scheduleDriftApply()`）——`_mutate` 的善后只做减法（`_removeDriftUnder`），而这些文件 revert 前是 `opened`（本就不在漂移集里），减法减不到任何东西；同时 mutation 自己的 watcher 事件被 `_suppressExternalChanges()` 抑制，两头都不补的结果是文件**在本会话彻底消失**，要等下个会话扫描才回来。查询失败只记日志、**绝不记成 clean**（漂移留给下个会话的扫描找到）。守卫见 `clientReconcileScan.test.ts` 的 `re-adds reverted files as drift…`。凡是「让文件从 opened 变回未签出」的新命令都要照此补这一步。
- **还原（统一入口）**：`perforce.revert` 按打开状态分流——已打开走 `revert(paths)` = `p4 revert`（离开 changelist + 丢本地改动）；未打开走 `revertReconcile(paths)` = `p4 clean`（旧「丢弃未收集的改动」）。确认框在含已打开文件时列出将离开 changelist 的文件（`revertPlan.ts`）。Explorer 目录去掉 `!explorerResourceIsFolder`，`openedInTree(dir)` 做 live `p4 opened dir/...` 预检后始终 `p4 clean dir/...`，有 opened / fail-open 才叠加 `p4 revert dir/...`。**目录判定走纯函数 `isRevertDirectoryTarget(selection, arg0.isDirectory)`**：Explorer 右键目录时菜单期总会把选区物化成 args[1] 且含 primary 自身，所以行右键只能判「selection 恰好只有那一个目录」；但空选区形态仍真实存在（Explorer 空区右键菜单无 args[1]、右键工作区根行 selection 被过滤成空数组、旧宿主），handler 须用 `selection[0]?.path ?? resolveTargetPath(args[0])` 兜底取目录路径，绝不能判 `selectionPaths(...).length === 0`——那是 06d94fa9 起的失效条件，让目录 revert 恒掉进逐文件分支静默无效果。多选混入目录项时并入 `plan.directories`（多目录经 `openedInTrees` 单条 `p4 opened <d1>/... <d2>/...` 批量预检）。`client.revertReconcile` 只作执行原语，不再有独立菜单/命令面板入口。
- **扫描范围（范围 ∩ 聚焦）**：`extension.ts` 的 `applyReconcileScope` 读 `workspace.focusEnabled`+`workspace.focusFolders`，经 `focusScope.ts` 的 `resolveFocusScope`（纯函数，注入 stat）拆成目录 / 文件两桶 → `client.setReconcileScope(dirs, files)`；扫描轮里 discovery = **日常范围 ∩ 聚焦**（`scopePartsWithin(base, focusTargets)`），两种引擎拿到同一结果。**除扫描之外什么都不跟随聚焦**：默认 get 的范围来自 `_applyScopeBase` 写下的 `_syncScopes`（范围自身的条目），行级徽标与每一条显式目标同样只受范围约束。只聚焦文件（没有目录项）时 δ 不参与（`scopeDirs.length === 0`），走原生逐文件阶段。范围外路径在 `_isInReconcileScope` 处过滤。

## Explorer 按需 hint 通道（`checkWorkingTree`）——未收集改动的行级徽标

未签出但磁盘偏离 depot 的文件在资源管理器文件行上显示**改动徽标**（M/A/D，与 git 状态字母一致）：一条**由 Explorer 当前渲染出来的文件行驱动**的按需查询通道——成本与可见行数同阶，与 depot 规模无关（绝不打开全量扫描，那正是「点击几分钟打不开 diff」的根因）。它与上节的常驻 reconcile 分组**并存**：分组是面板 / 文件夹染色 / 可操作性的完整真相，这条通道是行级改动徽标的按需发现。

链路：renderer `ScmWorkingTreeHintService`（pull 式，骨架照抄同目录 `ScmIgnoredResourcesService`：render 期问 → 150ms 去抖批量 → 缓存 + LRU 4096 → `version` observable 触发重渲染）→ capability 命令 `perforce.checkWorkingTree`（**运行时注册，绝不进 `contributes.commands`**，同头号坑）→ `client.checkWorkingTree(paths)` → 复用 `_rescanReconcilePaths` 的分批/并发/client 语法翻译。配置项 `perforce.reconcileHint.enabled`（默认开）可整体关掉。

**owner 仲裁必须按能力过滤**（`ScmService.ts` 的 `resolveScmProviderIdWhere`）：p4 workspace 内常有嵌套的独立 git provider（`git.repositoryScanMaxDepth` 命中的子目录）。裸最长前缀会让嵌套 git 胜出，而 git 侧从不注册 `checkWorkingTree` → `executeCommand` 返回 undefined → `_flush` 把整批路径当 clean 写进缓存，该行**再也不会重新入队**，症状就是「p4 确实有改动但 Explorer 永远不显示改动徽标」。所以最长前缀只在**注册了该能力**的 owner 里选（显式选中的 repo 仍优先，与既有语义一致）；无 capable owner 时**既不缓存也不入队**，这是能力晚注册（`checkWorkingTree` 在 `extension.ts` 注册，晚于 SourceControl 创建且不伴随 `sourceControls` 变更）能自愈的唯一原因——别为「省一次仲裁」把它改成写缓存。

四条决策，改这条通道前先对照：

- **本通道不写 SCM `resourceStates`**：`checkWorkingTree` / hint 服务只服务 Explorer 行，绝不写 `_reconcileGroup.resourceStates`——那是 `_applyDriftGroup()` 的专属职责（见上节）。但注意：`ScmDecorationsService` 确实会消费常驻 reconcile 组的 `resourceStates` 来给文件夹染色，二者靠**组**衔接，而非拆掉 hint 通道去喂装饰。
- **徽标从 `toReconcileResourceState` 派生**（`p4Decoration.ts` `toWorkingTreeHint`）：letter 复用该行的 `contextValue`——**git 对齐的动作字母加 `R` 前缀**（edit→`RM`、add→`RA`、delete→`RD`），与已签出行共用同一份 style 映射，保证徽标与行装饰观感一致。`R` 前缀是关键：字母改成与 git 相同的 M/A/D 后，`scmResourceState` 已无法区分「未收集」与「已签出」的同一动作，菜单门控改用组 id（`scmResourceGroup != reconcile`）；单测 `clientWorkingTreeHint.test.ts` 直接与 `toReconcileResourceState` 的返回值逐字段比对，改坏派生关系即红。
- **文件行出改动徽标；文件夹染色走 `ScmDecorationsService`，不靠本通道**：`ScmWorkingTreeHintService.getFolderHint` 现在只从 pull 通道已有缓存的文件 hint 聚合向上传播（删除红色 > 其余动作，同级按 source 键取小），作为**首轮扫描落地前的兜底下界**。权威的文件夹颜色是 `ScmDecorationsService`——它读常驻 reconcile 组 `resourceStates` 的整组替换（可回收），本通道不再有独立目录聚合表（旧的 `_scanFolders` / `onDidPublishWorkingTreeScan` 已删）——背景扫描一次 publish 上万条 hint 灌进按可见行数定容的 LRU 会自我抹除、还挤掉可见行刚查到的答案（根因教训）。仍是**已发现改动的下界**——未展开的子树查不到、保存/工作区切换也会让颜色增减，用户已确认接受该权衡；别为补全上界去做全量发现。
- **只读派生（最容易被"顺手优化"破坏）**：`checkWorkingTree` 绝不写任何共享状态、绝不持久化、绝不 `_emitChange()`。一旦有人想「既然都扫了不如存下来」，这条通道就退化成它要规避的全量发现。护栏 = store save spy + `onDidChange` 计数。

另两处易踩：hint 按两个谓词过滤（已 opened / scope 外），全被过滤掉则**零 p4 spawn**；返回值**回显调用方自己的路径字符串**（扫描报的是从 client 语法翻译来的路径，拼法未必与 host 一致，不回显会让 renderer 缓存键对不上，还会把没问过的路径——比如 rename 的另一半——报到不存在的行上）。

回显那张 map 的 key 必须是 `scopeKey` 而非 `norm`——它两侧**不同源**：请求方按用户打开目录的拼法给，答案按 `p4 info` 报的 clientRoot 拼，Windows/macOS 上两者可以只差大小写却指同一个文件（`norm` 只折盘符，会漏配 → hint 静默消失）。同一个方法里查 `_openedPaths` 仍用 `norm`，因为那个 set 的键与被比较的值同源（都由 p4 报）。`pathUtil.ts` 里 `scopeKey` 的注释就是这条判据的出处。路由用 `resolveContaining`（严格最长前缀）而非 `resolveClient`——后者的 active 回退是命令路由语义，数据查询用它会把不归任何 client 的路径扔给 active client 扫。

**⚠️ 根因 / 修法（在飞查询竞态）**：renderer 侧 `ScmWorkingTreeHintService` 的在飞标记必须带 per-request 令牌。曾经 `_inFlight` 是无身份的 `Set<string>`：p4 `reconcile -n` 往返 > 150ms 去抖时，同一 key 的两次查询必然重叠——保存文件触发的 `_onFileEvents` 删掉标记意在丢弃旧答案，但第二次 flush 又把它加了回来，于是先返回的旧（保存前）答案被接受写进缓存，后返回的正确答案反而被丢弃。后果是该文件被永久钉死成「干净」：缓存里有条目故不再重新入队，而 `_revalidate()` 只遍历 `_cache.keys()`，标记时还没进缓存的 key 漏标；`_generation` 只在 `_invalidate()` 里 bump 也救不了——症状与真正的「没有改动」完全无法区分。修法：`_inFlight: Map<string, number>` + 单调 `_queryToken`，`_writeHint` 只接受 token 匹配的答案（latest-wins），不匹配打一行 debug 日志；`getHint` 缓存 miss 分支加 `_inFlight.has(key)` 守卫，避免重渲染重复入队灌满 `ConcurrencyGate`。回归护栏在 `apps/editor/src/renderer/services/scm/__tests__/ScmWorkingTreeHintService.test.ts`（两个用例：「旧答案在重新查询已发出后才落地时被丢弃」「在飞期间不重复入队」）。

## Explorer 落后灰字（`checkBehind`）——可见行按需 fstat + 状态栏 chip 复用

「远端有更新 ↓」灰字与「他人占用 ✎」的驱动机制**不同**：✎ 由启动 `opened -a` 后台扫描推全量；↓ 由**可见行按需探测**驱动（旧实现是启动时全量 `sync -n` 扫描，已废弃）——renderer `ScmBehindHintService`（`apps/editor/src/renderer/services/scm/ScmBehindHintService.ts`，pull 式，与 `checkWorkingTree` 同款：渲染期问 → 150ms 去抖批量 → 缓存 + 在飞 token latest-wins）在 Explorer 文件行渲染时调 capability 命令 `perforce.checkBehind`（**运行时注册，绝不进 `contributes.commands`**，同头号坑）→ `client.checkBehind(paths)` 逐文件 fstat（`#have < #head` 即 behind）→ 返回 behind 子集给 host 停问，真正的 ↓ 装饰经 `setSupplementaryDecorations` **push**（`_publishSupplementaryDecorations` 单一收口）。行不渲染就不探测，成本与可见行数同阶、与 depot 规模无关。

**双通道缺一不可**：renderer pull 只负责**终止重复查询循环**（miss 缓存 false 让行不再重查），其返回值**刻意不做渲染**；真正的 ↓ 装饰必须由 perforce 侧 push——装饰的 description / tooltip（`↓#head`）只有 `_publishSupplementaryDecorations` 拿得到。两通道共享 `_setBehindFromInfo` 单一写入口。**循环安全**：supplementary observable 变更 → invalidate → re-render → re-probe → push → 又变更……靠 hostScm 的 `diffSupplementaryDecorations` **delta 去重**收敛（相同集合零 RPC），renderer 侧「supplementary 变更即全清失效」因此也安全。

红线（改动前逐条对照）：

- **checkBehind 走 background 优先级 + `CHECK_BEHIND_TIMEOUT_MS`（20s）紧超时**：滚 Explorer 被动触发的渲染路径突发，不是用户等结果的点击，绝不能占并发门静态预留的交互槽（见「共享 FIFO 并发门」节）。
- **behind/occupied 按路径合并成单一 marker**：renderer 按路径 key 装饰，两个独立条目会互相覆盖——合并收口在 `_publishSupplementaryDecorations`（`✎` + `↓` → 单一 `✎ ↓`，两半 tooltip 换行拼接，e2e merge journey 守护）。
- **状态栏 chip 复用**：`updateBehindFromFstat` 把状态栏 rev chip 已跑的 fstat 结果喂进 `_setBehindFromInfo`（chip 与可见行探针共用的单一漏斗），同一文件不跑第二次服务器查询。**sync 成功 → `_clearBehindDecorations()` + `_invalidateWorkspaceState()`**：装饰靠渲染触发 + push，sync 清掉 behind map 与 fstat 缓存后，下一次可见行渲染重新 fstat（have==head → 不再 behind）——fstat 短 TTL（`P4CacheNs.fstat` = `max(workspaceTtlMs, 15s)`）只吸收重复读突发，不是 behind 判定的持久层。
- **禁止恢复整仓 `sync -n` 预扫**：旧实现启动时全量 `sync -n`，真机活跃 depot 下每 5 分钟白烧一次 20s 超时；只用活动编辑器文件 + 可见文件行逐行 fstat。
- **失败 ≠ clean**：瞬时 fstat 失败（超时 / 连接抖动）**保留**已有 behind 标记，只把该路径从返回子集剔除（对照 `runOpenedByOthersScan` / `checkIgnore` 的「失败保留」先例）。
- **批量单次 republish**：`_setBehindFromInfo` 返回 boolean、**不自己 republish**；一轮结束时只发一次 `setSupplementaryDecorations`——否则 100 行重查 = 100 次 O(N) 全量 diff。
- **入口离线守卫**：`_connection !== 'connected'` 直接返回 `[]`。

**判据与锚点**：`fstatParser.ts` 的 `asRev` / `fstatBehind`（behind 判据 = `have < head` 且排除 `action === 'add'`、`haveRev === 'none'`）；契约在 `packages/extensions-common/src/contracts/dirtyDiff.ts` 的 `DirtyDiffCapabilities.checkBehind`（运行时注册、不进 `contributes.commands`）；e2e 回归 `extensions/perforce/e2e/specs/perforceStatusDecorations.spec.ts` 五用例（✎ / ↓ / 合并 / sync-clear / clean）。
